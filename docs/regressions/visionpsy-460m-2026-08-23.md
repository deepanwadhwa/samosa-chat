## Enforced resource behavior

- Images are decoded only after compressed-size and dimension/pixel-safety
  checks, then aspect-preservingly resized/normalized/retiled by the pinned
  processor.
- The gateway chooses 2048, 1536, 1024, or 512 maximum-side input from total
  RAM, live available memory, memory-pressure state, thermal state, and task
  detail. A 16 GB host starts no higher than 1536.
- Resource state is sampled before helper load and before each PDF page.
  Resolution can only downshift during a turn.
- Visual work is refused when live available memory is below 2.5 GB, memory
  pressure is critical, or thermal pressure is critical. Text/OCR or completed
  visual evidence is preserved as a labelled partial; vision-only work returns
  `vision_resource_pressure` and does not synthesize a factual answer.
- PDF page coverage comes from explicit/relevant/whole-document task scope.
  Internal five-page extractor calls are transport windows, not a product cap.

## Claim boundary and next release qualification

This run did not measure VisionPsy while a supported primary chat model and a
representative ordinary desktop workload were simultaneously resident. It
therefore does not establish combined peak memory, swap trend, thermal envelope,
text-LLM latency impact, or post-turn control-envelope recovery.

Before marketing the complete 16 GB combined workload as qualified, run paired
control/attachment trials for each supported active LLM and record those
metrics. Until then, the honest claim is: the exact native helper passed on the
16 GB M3 with a measured isolated peak RSS of 1,104.95 MB, and the gateway has
live downshift/refusal safeguards designed to preserve the rest of the system.
