## What landed

1. **Multi-page PDF fixture** — `tests/fixtures/documents/multipage_7pages.pdf`
   (7 pages, 2210 bytes), generated by `tools/gen_multipage_pdf.py` (byte
   offsets computed programmatically, not hand-typed). Validated against the
   **real** PDFium library already present on this machine at
   `~/Documents/samosa-pdfium-artifacts/chromium-7961/mac-arm64-unpacked/`
   (built `samosa-extract` from current `src/samosa_extract.c` against it):

   ```
   $ make samosa-extract PDFIUM_DIR=~/Documents/samosa-pdfium-artifacts/chromium-7961/mac-arm64-unpacked
   $ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 1 5
   {"ok":true,...,"page_count":7,"page_start":1,"page_end":5,...}      # exit 0
   $ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 1 100
   usage: samosa-extract --json FILE ...                               # exit 64
   $ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 6 2
   {"ok":true,...,"page_start":6,"page_end":7,...}                     # exit 0
   ```

   This **reproduces, with the real extractor binary and real PDFium, the
   exact T0.3 defect already named in CLAUDE.md/TASKS_UI_CHUTNI.md**: the
   gateway's initial cache-fill call at `src/samosa_gateway.c:2248` requests
   `COUNT=100` unconditionally, but `samosa_extract.c`'s `--json-pages` caps
   `COUNT` at 5 (`src/samosa_extract.c:562`) and exits 64 on anything larger.
   Every real PDF hits this on first read; `tests/test_compiled_gateway.sh`
   never exercises it because it substitutes a shell-script stub for
   `samosa-extract` that ignores the requested count. This fixture is now
   available for T0.3 to write a real regression test against.

2. **Fake model-download server** — `tests/fake_model_download_server.c`,
   built on the existing `tests/fake_openai_backend.c` / `src/samosa_http.h`
   pattern. Added one small additive field to the shared test HTTP request
   parser (`SamosaHttpRequest.range`, capturing the raw `Range:` header —
   previously discarded) so a test server can honor/mis-honor Range requests;
   rebuilt `samosa-gateway` and `test_fake_openai_backend` against the changed
   header to confirm no existing behavior changed (both compile clean under
   `-Wall -Wextra -Werror`, and the full existing suites below still pass).

   Modes implemented and exercised by `tests/test_fake_model_download_server.sh`
   (`make test-fake-download-server` — PASS): `normal` (valid 200 and valid
   206+Content-Range), `ignore_range` (200 despite a Range header),
   `truncate` (declares the full Content-Length, delivers fewer bytes),
   `corrupt` (correct length, wrong checksum), `bad_content_range` (206 with
   a Content-Range that cannot be reconciled with the request),
   `redirect` (302 to `192.0.2.1`, RFC 5737 TEST-NET-1 — guaranteed
   non-routable, never reaches a real host), and `oversize` (byte-correct
   response larger than a hypothetical catalog-declared size). These cover
   every failure mode T2.2's acceptance criteria name explicitly.

3. **Chutni folder-tree fixture generator** —
   `tests/fixtures/ui_chutni/gen_folder_fixture.sh`, a shared, reusable
   generator (not a one-off): `build`, `mutate-add`, `mutate-rename`,
   `mutate-delete`, `mutate-change`, `fix-perms` subcommands. Produces plain
   text, a real multi-page PDF, a real minimal PNG (hand-encoded via
   `zlib`/`struct`, not copied from another repo asset), a real ZIP
   (`unsupported_type` candidate), duplicate content at two paths, a hidden
   dotfile, an oversized file, a `chmod 000` permission-denied subtree, and
   two symlink-escape attempts (absolute and relative, both pointing at
   `/etc` — universally present, read-only, never actually traversed).
   Verified in `tests/test_chutni_folder_fixture.sh` (`sh
   tests/test_chutni_folder_fixture.sh` — PASS), including confirming the
   duplicate files are byte-identical, the PNG's magic bytes are real, the
   blocked directory is genuinely unlistable to a non-root process, both
   symlinks resolve outside the fixture root (checked via
   `os.path.realpath`), and `fix-perms` leaves a tree `rm -rf` can remove.

4. **Legacy-model and interrupted-download fixtures** —
   `tests/fixtures/ui_chutni/gen_legacy_model_fixture.sh` places placeholder
   files at the exact paths `backend_available()`/`load_config()` already
   check (`models/ornith-9b/...`, `models/bonsai-27b-1bit/...`), for T2.1's
   future legacy-detection tests. `tests/fixtures/ui_chutni/
   gen_interrupted_download_fixture.sh` builds the §5.3 on-disk partial-artifact
   layout (`~/.samosa/models/<id>/.partial/<job-id>/`) with a real 2048-byte
   partial file, paired with the frozen job-registry snapshot at
   `tests/fixtures/ui_chutni/contracts/interrupted_install_job.json`
   (`state:"paused"`, `completed_bytes:2048`, `total_bytes:8192`,
   `retained_partial_bytes:2048`) for T1.2/T2.2 to consume.

5. **Corrupt-index fixtures** —
   `tests/fixtures/ui_chutni/corrupt_index/{valid,truncated,bad_header,garbage,zero_length}.sqlite3`,
   authored by `tests/fixtures/ui_chutni/gen_corrupt_index_fixture.sh` using
   the system `sqlite3` CLI (a one-time authoring step only — per CLAUDE.md
   the shipped product never depends on a system SQLite at runtime; these
   are committed binary outputs, read by tests with no `sqlite3` dependency).
   Each corruption mode was verified against real `sqlite3 PRAGMA
   integrity_check`:

   ```
   valid.sqlite3:       ok
   truncated.sqlite3:   Error: in prepare, database disk image is malformed (11)
   bad_header.sqlite3:  Error: in prepare, file is not a database (26)
   garbage.sqlite3:     Error: in prepare, file is not a database (26)
   ```

   (`zero_length.sqlite3` is the empty-file edge case; not every corruption
   detector handles it the same way, which is exactly why it's a fixture.)

6. **JSON contract fixtures** — 19 golden files under
   `tests/fixtures/ui_chutni/contracts/`, transcribed verbatim from
   `docs/TASKS_UI_CHUTNI.md` §5 (error envelope, profile, setup status,
   conversation v2, catalog top-level + entry, install request/created/status,
   installs list, interrupted install job, selection request/created, fs
   roots/directories, Chutni preflight request/response, scope create
   request/summary, build job, forget request, query request/response
   (used + unused), job event, chat request context). Validated by
   `tests/test_ui_chutni_contracts.py` (17 tests, `python3
   tests/test_ui_chutni_contracts.py` — OK), which also exposes a reusable
   `assert_contract_shape()` helper for future endpoint tests to check a live
   response against the same frozen fixture, plus closed-enum checks for every
   documented state machine (scope kind/state, freshness state, install job
   state, selection state, durable job state, setup `next_step`, and the
   Chutni stable-error-code/skip-reason lists).

   **One doc-authoring quirk found while transcribing:** at
   `docs/TASKS_UI_CHUTNI.md:976-994`, the label "Forget requires:" precedes a
   JSON block whose fields (`job_id, scope_id, kind, state, phase,
   evidence_generation_target, status_url, events_url`) are structurally the
   **build/refresh/rebuild job-creation response**, not a forget request — the
   real forget-request shape (`{confirm, client_request_id}`) appears later
   under a second "Forget requires:" label at line 1000. Treated the first
   block as `chutni_build_job.json` and the second as
   `chutni_forget_request.json` by their actual field shapes; flagging this to
   the doc owner rather than silently editing the frozen spec.
