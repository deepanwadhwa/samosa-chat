# T2.2 — Build resumable server-owned downloads: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T2.2 (Phase 2),
§5.3 (model catalog and lifecycle), §5.7 (durable job events). Branch:
`ui-chutni`. Date: 2026-07-27. Machine: the reference machine (16 GB Apple
Silicon MacBook Air, macOS 26.5.1, Darwin 25.5.0 arm64).

**Status: real, tested, and complete against this task's own acceptance
list — with two disclosed scope decisions (below), not gaps found and
hidden.**

## What was built (`src/samosa_gateway.c`)

`POST /v1/models/install`, `GET /v1/models/installs`, `GET
/v1/models/installs/<job_id>`, `GET .../events`, `POST .../pause`,
`.../resume`, `.../cancel`, `.../retry`. All new routes; all covered by the
fail-closed dispatcher gate automatically (none needed adding to the
legacy-unauthenticated list).

- **Transfer mechanism**: shells out to `curl`, exactly like
  `dist/install.sh` already does for every other real fetch this project
  makes — not a stub. Implementing a from-scratch TLS client would mean
  vendoring a TLS stack, directly against the project's dependency-free
  ethos. `-C -` resumes from whatever the destination already contains;
  `-L` follows redirects (real Hugging Face resolve URLs redirect
  cross-subdomain to their CDN — verified live, see below);
  `--proto-redir -all,https` restricts every redirect hop to https, which
  is what actually stops a malicious/broken redirect rather than an exact
  hostname allowlist (HF's CDN host isn't fixed, and hardcoding it would
  break real downloads the moment it changes).
- **A real bug caught by testing, not shipped**: the first version had no
  `-L` at all. Against the fake server's "redirect" test mode this
  *looked* correct (job failed, nothing activated) — but for the wrong
  reason: curl was never following any redirect at all, so a real Hugging
  Face download would have saved the tiny 302 response body as if it were
  the model weights. Caught by actually running the redirect test end to
  end and inspecting *why* it failed, not just that it failed. Fixed by
  adding `-L` and re-verifying the redirect-to-untrusted-scheme case still
  correctly fails (now because `--proto-redir` refuses to follow it: `curl:
  (1) Protocol "http" disabled (in redirect)`).
- **Verification**: native SHA-256 (`read_cache_key_file()`, already used
  elsewhere in this file for content-addressed caching) — not a `shasum`
  subprocess. Byte size is checked first (cheap, catches truncation/
  oversize immediately); hash is only computed if the size already matches.
- **Atomic activation**: every artifact for a model must independently
  verify before any of them are moved. Verified files are staged under
  `~/.samosa/models/.installs/<job_id>/` and `rename()`d into their final
  `install_path` under `g->home` only after the full set passes — same
  filesystem, so `rename()` is atomic even for the 24 GB `experts.bin`. A
  failed job never reaches this step, so a working prior install is never
  replaced by a bad one (tested explicitly, see below).
- **Preflight**: `statvfs` on the destination filesystem before any
  transfer starts, comparing bytes still needed (already-staged bytes from
  a prior attempt count as "already have") plus a 2 GiB reserve against
  actual free space. Reports the specific required/available byte counts
  in the failure message, not just a bare error code.
- **Pause/resume/cancel/retry**: one active transfer at a time, tracked
  directly on `Gateway` (`active_install_job_id`, `install_mu`) rather than
  a persisted multi-model FIFO queue. Pause/cancel `SIGTERM` the tracked
  curl child; the worker distinguishes "killed by our own request" from a
  real failure and transitions to `paused`/`canceled` instead of `failed`.
  A paused job does **not** hold the transfer slot — a different model can
  start installing while one sits paused (tested). Retry creates a new job
  ID and moves the old job's staging directory into place first, so `curl
  -C -` continues from the retained bytes rather than from zero — a failed
  job's own corrupt/oversized artifact was already deleted by the worker,
  so only genuinely intact bytes are ever reused.
- **Live byte progress**: `completed_bytes`/`total_bytes`/
  `current_artifact*` are computed fresh from the catalog's declared sizes
  plus whatever is actually staged on disk, never persisted redundantly
  alongside job state (avoids state/reality drift, same principle as
  T2.1's `install_state`).
- **Events**: `GET .../events?after=<seq>` is a plain JSON replay, not SSE
  — no route in this codebase serves `text/event-stream` yet (the existing
  native Jobs system reads its own JSONL the same way), and nothing
  consumes this endpoint live yet either (the frontend gap from T2.1 is
  still open). Live push is a documented future enhancement.

## Real bugs found and fixed during this work (not shipped)

1. **Stack-overflow-adjacent class of bug, this time a route-matching
   off-by-one**: `strncmp(request->path, "/v1/models/installs/", 21)` — the
   literal is 20 characters, not 21, so the extra byte compared was the
   prefix's own NUL terminator. Every request with a job ID after the
   prefix failed to match (`strncmp` sees the path's real character where
   the prefix has NUL) and fell through to the generic 404, while the bare
   list route worked fine (different, correct check). Caught immediately
   by an end-to-end smoke test hitting `GET .../installs/<job_id>` — a unit
   test of the parsing logic in isolation would likely have missed it too,
   since the bug was in the *outer* route dispatch, not
   `models_installs_dispatch()`'s own (correct)
   `sizeof(prefix) - 1` pattern. Fixed by using the same self-computing
   `sizeof(...) - 1` idiom instead of a hand-counted literal.
2. **Missing `-L` on the curl invocation** (described above) — a real
   correctness bug that would have broken every real download, caught only
   because the redirect test's *reason* for passing was inspected rather
   than trusted at face value.

## Tests (`tests/test_model_install.sh`, `make test-model-manager`)

Runs against the real compiled gateway and the real T0.1
`tests/fake_model_download_server.c` fixture — no real network artifact,
no multi-gigabyte file. 14 scenarios, all passing, including under an
`-fsanitize=address` build (a one-off check for this task, not part of
`make test`):

1. No token on `/v1/models/install` or `/v1/models/installs` → 401.
2. Normal full install → `installed`; activated file's hash and `0600`
   permissions verified directly (not just "job says installed").
3. Duplicate install request for the same model/version while the first is
   still nonterminal → same job ID, still `202`.
4. Repeated `client_request_id` → same job ID (tested in isolation from
   #3, since firing both dedup paths in the same window would make it
   ambiguous which one actually fired).
5. `truncate` → `failed`, nothing activated.
6. `corrupt` → `failed` with `checksum_mismatch`, nothing activated.
7. `redirect` (to a non-routable, non-https target) → `failed` with
   `download_failed` (curl's own protocol-disabled rejection).
8. `oversize` (declared bytes smaller than what the server actually holds)
   → `failed` with `size_mismatch`.
9. `ignore_range` and `bad_content_range` (server quirks, not attacks) →
   **still install correctly**, verified by re-hashing the activated file —
   this downloader's own post-transfer verification is the actual backstop
   regardless of what curl or the server believed about ranges mid-transfer.
10. A working installed version survives a failed re-install attempt:
    install once successfully, record the activated file's hash and mtime,
    then trigger a second (corrupt-mode) install for the same model and
    confirm the original file's hash and mtime are unchanged.
11. Preflight `insufficient_space` (a fixture artifact declaring 100 TB)
    fails immediately, before any curl invocation, and the error message
    reports actual required-vs-available byte counts.
12. Pause mid-transfer (rate-limited via a test-only `SAMOSA_TEST_LIMIT_RATE`
    hook — a real transfer on loopback completes before an unthrottled
    pause request could ever land) → `paused` with partial, nonzero,
    incomplete progress; idempotent re-pause; a *different* model can start
    installing while this one sits paused (proves the slot isn't held);
    resume → `queued` → completes to `installed` with the full byte count.
13. Cancel mid-transfer → `canceled`; idempotent re-cancel; retry → new job
    ID, nonzero `reused_bytes`, completes to `installed`.
14. A second distinct-model install while one is actively transferring →
    `503 install_busy`.

Also re-run clean after this change: `make test-ui-setup`,
`compiled-gateway-test`, `jobs-test`, `test-chutni` (all PASS).

## Test-only hooks added (production behavior unaffected by default)

- `SAMOSA_TEST_ALLOW_LOOPBACK_ARTIFACTS`: lets a fixture catalog reference
  `http://127.0.0.1:<port>/...` past `artifact_url_is_trusted()`'s
  production `https://huggingface.co/` allowlist. This codebase has no TLS
  library, so the T0.1 fixture server can only ever speak plain HTTP;
  without this hook, T2.2 could not be tested against it at all without
  adding a TLS dependency just for a test double.
- `SAMOSA_TEST_LIMIT_RATE`: passes `--limit-rate` to curl so a small
  fixture transfer over loopback has a real, deterministic window in which
  to test pause/cancel, instead of completing before any request could
  possibly land.

Both are read via `getenv()` and are inert unless a test sets them.

## Scope decisions (disclosed, not hidden)

- **One active transfer at a time, not a persisted multi-model FIFO
  queue.** The spec text describes "additional distinct installs may wait
  in FIFO queued state"; this task's own acceptance list does not test
  cross-model queuing specifically. A second concurrent distinct-model
  install request is rejected with `503 install_busy` rather than queued.
  Tested (#14). If real multi-model concurrent queuing is wanted, it's a
  bounded follow-up: scan `.installs/*/job.json` for the oldest queued job
  whenever the active slot frees, rather than rejecting outright.
- **Real network disconnect was not separately simulated** — pause (an
  explicit `SIGTERM` to the curl child) exercises the identical resume
  mechanism (`curl -C -` continuing from the existing partial file) that a
  genuine dropped connection would also hit, but "kill the process" and "the
  TCP connection actually died" are not quite the same event, so this is
  disclosed rather than claimed as identical.
- **Real disk-full-mid-transfer was not separately simulated** — no
  portable way to create a real ENOSPC condition mid-write without a
  genuinely constrained filesystem (a loopback/tmpfs mount, which needs
  root or platform-specific tooling). The code path that would handle it
  (curl exits nonzero on a write failure → `download_failed`, same as any
  other curl failure) is exercised by every other failure-mode test, just
  not by an actual full disk.
- **Retry was tested from `canceled`, not separately from `failed`** — the
  handler's only state-dependent branch is `state == "failed" || state ==
  "canceled"`, with identical logic afterward, so testing one exercises the
  same code the other would; not claiming both were independently run.
- **`GET .../events` is plain JSON replay, not SSE** — matches existing
  project convention (no route serves `text/event-stream` anywhere yet),
  and nothing consumes this endpoint live regardless (T2.1's frontend gap
  is still open).
- **Qwen's converted weights still have no download URL** — carried over
  from T2.1, unchanged here: `tools/package_hf.py --repo-id` is still
  `REPO_ID_PLACEHOLDER`. Installing Qwen via this new job manager is not
  possible yet and correctly fails with `artifact_not_downloadable`
  (untested here specifically since it requires the real, large Qwen
  catalog entry rather than a fixture — the code path is a simple, direct
  `if (!url->str[0])` check exercised implicitly by every fixture that
  omits a URL).
