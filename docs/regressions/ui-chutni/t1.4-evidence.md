# T1.4 — Migrate and bind conversations: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T1.4 (Phase 1),
§5.2 (conversation schema and migration). Branch: `ui-chutni`. Date:
2026-07-26. Machine: the reference machine (16 GB Apple Silicon MacBook Air,
macOS 26.5.1, Darwin 25.5.0 arm64).

## Scoping decision, stated plainly

T1.4's own spec entry lists `T2.1` and `T2.3` as dependencies "for immutable
model identity and readiness" — neither exists yet; they're unstarted Phase 2
(Model Manager workstream) tasks. Rather than block T1.4 on that work, this
follows the exact precedent T1.2 already set in `setup_status_handler()`
(`src/samosa_gateway.c`, comment: *"a selected, verified model does not exist
as a concept yet ... T2.1/T2.2 replace this with real state"*): build the real
schema, migration, and enforcement logic now, with model identity keyed to an
explicitly documented interim placeholder instead of a real catalog.

`active_model_id()`/`active_model_version()` (`src/samosa_gateway.c`) are that
placeholder: `model_id` is the backend name (`"qwen"`/`"bonsai"`/`"ornith"`,
matching the existing `setup_status_handler` convention and the T0.1 contract
fixture's `"model_id": "qwen"`); `model_version` is the basename of that
backend's configured model file — a real fact about the current install, not
a fabricated string, but not a content hash either. **When T2.1 lands, every
conversation bound under this placeholder needs the same schema-version
migration path this task already builds for v1 → v2** — that follow-up is
called out in code comments at both definition sites so it isn't lost.

## Backend (`src/samosa_gateway.c`)

### Canonical binding storage and `GET`/`PUT /v1/conversations/<id>/binding`

Binding metadata lives at `<home>/chats/<conversation-id>/metadata.json` —
the exact directory `backend_start()` already creates and hands to the qwen
backend via `SAMOSA_CHATS_DIR` for its own `session.qws` KV-cache file, so
both files end up side by side under the one conversation-id directory the
spec names. `valid_conversation_id()` mirrors the existing `valid_job_id()`
charset check (letters/digits/dash/underscore only) since conversation IDs
are client-generated and become a directory name on disk.

- `GET`: `404 conversation_unbound` if no record exists (including a record
  that fails to parse — treated as absent, not a crash).
- `PUT`: requires `model_id`/`model_version`; create-once — an identical
  repeat `PUT` returns the existing record unchanged (idempotent, `created_at`
  preserved); a `PUT` naming a different model on an already-bound
  conversation returns `409 conversation_model_mismatch`.
- Both routes are gated by `require_ui_session()`, the same token+Origin
  check every v1 route added since T1.2 uses.

### `/v1/chat/completions` binding validation (`chat_completions_request()`)

Wraps `proxy_request()` rather than replacing it. When the request body names
a `conversation_id`:

1. `model_id`/`model_version` must also be present (`400
   model_identity_required`) — the OpenAI-compatible stateless path (no
   `conversation_id`) is completely untouched and still falls straight
   through to `proxy_request()`.
2. If a model is actually active, the named `model_id`/`model_version` must
   match it exactly, or `409 conversation_model_mismatch` — this is what
   stops a stale tab or a direct API client from silently continuing under
   whichever backend happens to be loaded.
3. If no canonical binding exists yet for this conversation, one is created
   now (`model_binding_source: "explicit"`) — the *first* successful turn is
   what binds a conversation, matching the frontend's create-once stamping
   (below). If one already exists, it must match, or `409`.
4. Only after all of that does a single byte reach the backend.

If no model is active/ready at all, the new checks are skipped entirely and
control falls through to `proxy_request()`'s pre-existing `409 model_required`
/ `503 backend_loading` — those are the clearer, already-correct signals for
that case; this task doesn't touch them.

**Known residual gap, stated rather than hidden**: unlike the real selection
lock T2.3 is expected to add, this does not hold `g->mu` across the read of
`g->backend` and the eventual `proxy_request()` connect. A backend switch
racing a chat request already has a narrower, pre-existing TOCTOU in
`/v1/backends/select` (check-then-mutate, not one held lock) — this task
does not close that gap, it just doesn't make it any wider. Closing it for
good is T2.3's job. Documented at the top of `chat_completions_request()`.

### `/healthz` and `/v1/setup/status` now report a real `model_version`

Both previously hardcoded `active_model_version` (or omitted it from
`/healthz` entirely). Since the frontend needs *some* source of truth for
"what model/version is active" to send with chat requests, and
`/v1/setup/status` is already the only place that concept was exposed, this
fixes it to use the same interim helper rather than inventing a second
placeholder — not scope creep, the same concept T1.4 already needs wired
through the one place it already partially existed.

## Frontend (`assets/app.html`)

### Schema v1 → v2 migration

New storage key `samosa-chat-v2`; `samosa-chat-v1` is **only ever read**,
never written or deleted by migration code, so a failed migration always
leaves the original data recoverable. `loadState()`:

1. Returns an existing, valid `v2` state immediately (idempotent — a refresh
   after a successful migration never re-touches `v1`).
2. Otherwise attempts `migrateStateV1ToV2()` (pure, testable independent of
   `localStorage`): a malformed individual chat record is skipped, not fatal
   to the whole migration; every surviving chat gains
   `schema_version/model_id/model_version/model_binding_source/created_at/
   updated_at/directory_context` while keeping its original `created`/
   `updated` epoch fields (the current, not-yet-redesigned UI still sorts by
   them).
3. **Every** pre-T1.4 conversation gets `model_id: null,
   model_binding_source: "unknown"` — never an inferred model — because
   nothing before this task recorded which backend/version produced it, and
   §5.2 says plainly: *"the immutable version cannot be established ...
   Do not create a false binding."* It binds explicitly the next time a
   message is sent in it, under whichever model is active then.
4. The migrated state is written to the v2 key and **read back** before it's
   trusted; a write or readback failure (quota, storage error) is treated
   identically to malformed source JSON — fall back to a safe empty
   in-memory state, leave `v1` completely untouched, and flag
   `migrationRecoveryRaw` so a small dismissible banner (`#migrationBanner`)
   can offer "Export as a file" (downloads the untouched raw v1 string) or
   "Reset local chat storage" (clears both keys after a confirm).

### Model-binding stamping and mismatch dialog

`ensureChat()` now creates every new conversation unbound
(`model_id: null, model_binding_source: "unknown"`). `sendPrompt()` stamps it
explicitly on first send (`model_id`/`model_version` from the active
`backend`, `model_binding_source: "explicit"`) and includes those fields in
both request-shape branches (`qwen` and non-`qwen`) sent to
`/v1/chat/completions` — the same moment the gateway's create-once binding
fires.

`chatNeedsExplicitAction(chat, backend)` is the pure decision function: a
conversation with no recorded model is never a mismatch (it just binds on
next send); one whose `model_id`/`model_version` differs from the currently
active model is. `selectChat()` and `sendPrompt()` both check it before
proceeding — reopening a mismatched conversation opens a dialog
(`#mismatchDialog`, reusing the T1.3 chooser's dialog styling/scrim
convention) instead of silently switching. The dialog is honest about what's
actually possible today: "Fork into a new conversation" (real — copies
visible messages, the fork itself starts unbound) and "Cancel" are the only
buttons. Installing or switching to that exact model — two of the four
options the spec's acceptance criteria imagine — isn't implemented; the
dialog says so in its body text rather than showing dead buttons, since
neither is possible before T2.1/T2.3 exist.

## Two real bugs found while building this

1. **Route dispatch used the wrong prefix length.** `strncmp(request->path,
   "/v1/conversations/", 19)` — but `"/v1/conversations/"` is 18 characters;
   `19` included the string literal's own NUL terminator in the comparison,
   which only matches a path that is *exactly* `"/v1/conversations/"` with
   nothing after it. Every real request
   (`/v1/conversations/<id>/binding`) would have silently 404'd through to
   the final fallback instead of reaching the new handler at all. Caught by
   manual review before any test ran (counting the literal by hand against
   the `sizeof(prefix)-1` computed length used two lines later inside
   `conversations_dispatch()` itself, which is correct) — not caught by a
   failing test, which is itself worth recording honestly: the live-gateway
   test below would have caught it regardless (every binding-endpoint
   assertion would have failed with 404), but it never got the chance to.
2. **The DOM-fixture test's own stub gave a false pass.** Two compounding
   issues in `tests/test_conversation_migration_ui.mjs` while writing the
   `selectChat` mismatch test: (a) the hand-rolled `Element` class defaulted
   `.hidden = false`, not matching the real markup's `hidden` attribute, so
   an assertion that the dialog "became visible" passed trivially whether or
   not `openMismatchDialog()` was ever called; (b) `let backend = {...}` and
   `let generating = false;` are declared *inside* the exact source range
   sliced out for evaluation (between the migration code and `selectChat`),
   so a pre-set `globalThis.backend` was silently shadowed by the sliced
   block's own default (`version:""`), which made every mismatch check
   evaluate false regardless of the test's intent. Running the test caught
   this immediately — the `currentId` assertion failed even though the
   (falsely-passing) dialog-visibility assertion right before it did not —
   which is what prompted checking *why* a "passing" dialog check coexisted
   with a conversation switch that should have been blocked. Fixed by
   defaulting the dialog/scrim/banner stubs to `hidden: true` (matching the
   real markup) and exposing a `getBackend()` accessor from the eval'd
   closure so the test mutates the *real* binding via `Object.assign(...)`
   instead of a same-named global that was never actually in scope.

## Acceptance criteria

- **"A populated legacy browser profile migrates without lost messages."**
  Covered: `migrateStateV1ToV2()` test with a well-formed chat (messages
  preserved verbatim) alongside a malformed one (missing `messages`) in the
  same source state — only the malformed record is dropped, matching "A
  malformed conversation does not erase healthy conversations" below.
- **"Refresh during migration is safe."** Partially covered, stated
  honestly: the "already-migrated v2 state short-circuits re-migration" test
  proves a *second* `loadState()` call (simulating a refresh *after* a
  completed migration) never re-touches `v1` and returns the same v2 state.
  What is **not** verified: an interrupt truly *mid*-`localStorage.setItem`
  (e.g. a tab closing between the write and the readback). This harness has
  no way to simulate that; the design (write, then read back before trusting
  it, `v1` never touched either way) is the standard mitigation, but its
  behavior under a real mid-write interrupt was not measured.
- **"Browser-quota failure and malformed top-level JSON preserve the
  original localStorage key."** Covered directly: both a `setItem` throw and
  a malformed `v1` string leave the fake storage's `v1` entry byte-identical
  to what was there before `loadState()` ran.
- **"Reopening a conversation created by another model prompts for an
  explicit action."** Covered: `selectChat()` on a conversation bound to a
  different model opens the dialog and leaves `currentId` unchanged; the
  live-gateway test's server-side half is the `409` case below.
- **"A direct request carrying the wrong active model receives `409
  conversation_model_mismatch` and is not forwarded."** Covered in
  `tests/test_conversation_binding.sh` against a real gateway process and
  the repo's fake OpenAI-shaped backend standing in for a ready model: a
  request naming the wrong `model_id` gets `409`, and the response body is
  asserted to **not** contain the fake backend's `"compiled reply"` marker —
  proving the request never reached it.
- **"A malformed conversation does not erase healthy conversations."**
  Covered on both sides: frontend, via the skipped-bad-record migration test
  above; backend, via a hand-corrupted `metadata.json` for one conversation
  ID reading back as `404` (not a crash) — this is structurally guaranteed
  rather than merely tested for the multi-conversation case, since each
  conversation's binding is an independent file under its own
  `chats/<id>/` directory with no shared index that a corrupt sibling file
  could ever touch.

## What T1.4 does not include

- Real per-install immutable model identity/version (T2.1). Everything here
  is keyed to the documented interim placeholder; see the scoping section
  above.
- A real selection lock serializing model switching against chat admission
  (T2.3). The existing, narrower TOCTOU in `/v1/backends/select` is
  unchanged, not widened.
- "Install that exact version" / "switch to it if installed" in the
  reopen-under-another-model dialog — both require T2.1/T2.3 and are stated
  as unavailable in the dialog copy rather than faked.
- Full server-side transcript persistence — the spec explicitly says this
  can be added later; only gateway-enforced binding metadata is required
  now, and that's what this task builds.
- A real interactive browser click-through of the migration banner or
  mismatch dialog. Same limitation as T1.3: no browser-automation tool
  exists in this environment. What's verified is `node --check` on the
  extracted script plus the DOM-fixture suite described above.
