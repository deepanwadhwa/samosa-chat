# T1.0 — Produce a model-free browser runtime package: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T1.0 (Phase 1).
Branch: `ui-chutni`. Date: 2026-07-27. Machine: the reference machine (16 GB
Apple Silicon MacBook Air, macOS 26.5.1, Darwin 25.5.0 arm64).

## Scope note

T1.0 packages the already-working control plane; it does not define
zero-model gateway behavior (that's T1.1, done, and reused here unchanged).
T1.1/T1.2/T2.1 were all already DONE, so this task's dependency chain
(T1.1 → T1.2 → T2.1 → T1.0) was fully unblocked at the start.

## What landed

1. **`tools/package_hf.py`**: the compiled gateway + filesystem sidecar
   (`samosa_gateway.c`, `samosa_fs.c`, `read_cache.h`, `durable_job.h`) moved
   from the opt-in `--gateway` flag into the unconditional `SOURCE_FILES`
   list — every release now includes them, full stop. Added `--runtime-only`,
   which skips `MODEL_FILES` and the tokenizer entirely (no `--snapshot`/
   `--tokenizer` needed) and stages only the control plane: engine sources,
   gateway, app shell, and the model **catalog** (`assets/models.json` —
   control-plane data, not a model weight, so it's staged unconditionally in
   both modes; see "real bug" below).
2. **`dist/install.sh`**: `MODEL_FILES` (`experts.bin`, `resident.safetensors`,
   `manifest.json`, `config.json`, `generation_config.json`,
   `tokenizer_qwen36.json`) are now staged only if the release manifest
   actually lists them — a runtime-only manifest lists none, so nothing is
   requested. The old `GATEWAY_ENABLED` conditional (compile the gateway only
   if the manifest happened to include it) is gone; the gateway, jobsd, and
   fs sidecar are now unconditionally compiled, matching "mandatory browser
   control plane, not an optional package with a raw-Qwen fallback." The
   `$STAGE/model` directory is no longer eagerly pre-created (see real bug
   #2). The mandatory real-model generation smoke (POST
   `/v1/chat/completions`, assert `"choices"`) is replaced by a
   control-plane smoke: `/healthz`, root UI, `/v1/profile` (200 or the
   honest fresh-install 404 `profile_not_found`), `/v1/setup/status`,
   `/v1/models/catalog`, and a chat check that accepts either a real 200
   completion **or** 409 `model_required` — it asserts the shape of whichever
   one is true, never forces generation.
3. **`dist/samosa`**: `serve_foreground()`/`start_server()` no longer branch
   on `[ -f "$GATEWAY" ]` with a raw `qwen36b --serve` HTTP fallback — they
   require the gateway (`[ -x "$GATEWAY" ] || fail "... reinstall Samosa"`)
   and always exec it. The separately-named one-shot CLI path (`samosa
   "<prompt>"`, no `serve`/`app` subcommand) is untouched — it still calls
   `$ENGINE` directly and cannot masquerade as the browser app, satisfying
   "preserve a deliberate raw engine/headless path only if named separately."
   `doctor` no longer reports installation failure (`ok=0`) merely because no
   Qwen model is installed — a model-free runtime is now a normal, supported
   state, so it prints `model: none installed yet - open the app or run
   'samosa pull' to install one` and leaves `ok` alone; format/tokenizer
   checks only run once weights actually exist.

## Two real bugs found by testing before this landed

1. **The `RELEASE_DIR` heuristic in `dist/samosa` used model presence as a
   proxy for "am I in a real release directory."** `elif [ -x
   "$SELF_DIR/qwen36b" ] && [ -d "$SELF_DIR/../model" ]` fell through to
   `RELEASE_DIR=$HOME_DIR` (instead of `$HOME_DIR/current`) whenever
   `current/model` didn't exist — which is now the **normal** case for a
   model-free install. Every path the wrapper computes (`ENGINE`, `GATEWAY`,
   `TOKENIZER`, `APP_HTML`, `APP_LOGO`) would then point at the wrong
   directory the instant a real end user ran `~/.samosa/bin/samosa serve`
   (or `doctor`) after a clean runtime-only install — this wasn't caught by
   the installer's own internal smoke test only because that smoke
   explicitly overrides `SAMOSA_RELEASE_DIR`, sidestepping the heuristic
   entirely. Found by `tests/test_runtime_only_release.sh` invoking the real
   top-level launcher stub exactly as an end user would. Fixed by checking
   for the sibling `samosa-gateway` binary instead of the model directory —
   both engine and gateway are mandatory runtime binaries staged in the same
   `bin/` directory regardless of model state, so this signal is correct in
   every case, not just the model-free one.
2. **`install.sh` unconditionally pre-created `$STAGE/model`** (`mkdir -p
   "$STAGE/model" "$STAGE/engine" "$STAGE/bin"`) even when the manifest had
   no model files to put there, so a "model-free" install still produced an
   empty `current/model` directory. Harmless to `backend_available()` (it
   checks for the `experts.bin` *file*, not the directory), but it
   contradicted the acceptance line ("every model weight and backend model
   path absent") literally. Fixed: the directory is created lazily by
   `fetch()`'s own `mkdir -p "$(dirname "$target")"`, only when an actual
   model artifact is staged.
3. **(Packaging gap, not a code bug, but real):** `GET /v1/models/catalog`
   would 500 on *every* release built by `tools/package_hf.py` before this
   task, runtime-only or not — the catalog handler reads a bundled
   `models.json` asset that packaging never staged. This was disclosed
   explicitly in the T2.1 evidence doc ("T1.0 ... `tools/package_hf.py`
   wiring for `models.json` as a staged release asset ... was explicitly not
   started here"). Fixed by adding `assets/models.json` to the unconditional
   dist-file tuple in `package_hf.py` and to `install.sh`'s mandatory
   `INSTALL_FILES`/`destination()` mapping.
4. **The installer's own smoke test never isolated `SAMOSA_HOME`.** It set
   `SAMOSA_RELEASE_DIR="$STAGE"` (redirecting the engine/app/gateway paths
   `dist/samosa` itself computes) but left `SAMOSA_HOME` unset, so every
   gateway-internal default that depends on it (`profile.json`,
   `models_catalog`, `jobs_root`, the selection file) silently fell back to
   the *real developer machine's* `~/.samosa` — invisible before this task
   because the original smoke only touched `/healthz`, root `/`, and
   `/v1/chat/completions` (which gets its engine/model paths from the
   explicit `SAMOSA_QWEN_*` overrides, not `SAMOSA_HOME`). Adding the
   profile/setup/catalog checks this task's acceptance requires would have
   made the smoke nondeterministically depend on, and potentially write to,
   whatever the real operator's own `~/.samosa` happened to contain. Fixed:
   the smoke now sets its own throwaway `SAMOSA_HOME="$STAGE/.smoke-home"`
   and an explicit `SAMOSA_MODELS_CATALOG="$STAGE/models.json"`.

described.

## Acceptance criteria

- **"The installed browser runtime boots with every model weight and
  backend model path absent and remains alive."** Done —
  `tests/test_runtime_only_release.sh` installs a runtime-only release for
  real and confirms `current/bin/{samosa-gateway,samosa-fs,qwen36b}` and
  `current/app.html` exist while `current/model` does not, and the control
  plane serves through the full smoke.
- **"`/healthz`, root UI, profile, setup, and catalog work; Chat returns
  `409 model_required`."** Done — the rewritten install.sh smoke checks all
  five for real; the same fixture proves Chat returns 409 `model_required`
  with zero models installed.
- **"A fixture server records zero model-artifact requests during runtime
  install and upgrade."** Done — `tests/test_runtime_only_release.sh` serves
  the release over a real logged HTTP server and greps the log for each of
  the six model artifact names after both a clean install and an upgrade
  (repackaged with different runtime bytes, forcing a new `RELEASE_ID`);
  zero matches both times.
- **"Upgrading around a registered legacy model leaves its path,
  inode/identity, and bytes unchanged."** Done — the same test plants a
  legacy `~/.samosa/model/experts.bin`, records its inode, mtime, and
  SHA-256 before the clean install, and re-asserts all three unchanged after
  both the install and the upgrade.

## Disclosed scope decisions, not silent gaps

- **`llama-server` (Bonsai/Ornith's shared runtime dependency) is still not
  bundled by packaging.** `dist/samosa doctor` only *detects* an existing
  `~/.samosa/backends/prism-llama.cpp/build/bin/llama-server`; no script in
  `dist/` or `tools/` builds or downloads it. This predates this task and
  isn't something this change introduces or extends — it's a real gap
  against the spec's "every v1 runtime dependency ... is installed/upgraded
  by T1.0 on each supported target," but bundling a full llama.cpp build is
  a much larger, separate undertaking than model-free packaging, and remains
  open.
- **The root `Dockerfile` was left untouched.** It's stale (`COPY
  tools/samosa_gateway.py`, a file that no longer exists — the gateway has
  been a compiled C binary since Gate 11) and is explicitly issue #2's
  territory (`docs/TASKS_WINDOWS.md` D-3, which describes container
  packaging as "nothing exists" — a claim this file, sitting on this
  branch, actually contradicts). Fixing container release assembly belongs
  to that issue, not this one; flagging it here rather than quietly
  reaching across issue boundaries.
- **`assets/models.json` is bundled as-is** (already a real, independently
  verified catalog per the T2.1 evidence doc — this task only wires it into
  packaging, it doesn't re-verify its contents).
