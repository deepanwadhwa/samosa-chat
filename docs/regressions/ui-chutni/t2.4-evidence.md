# T2.4 — Ship Name → Welcome → Model → Chat: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T2.4 (Phase 2), §4.1–4.3
(user experience contract) and §5.1 (setup-status contract). Branch: `ui-chutni`.
Date: 2026-07-27. Machine: the reference machine (16 GB Apple Silicon MacBook
Air, macOS 26.5.1, Darwin 25.5.0 arm64, Apple clang 21.0.0).

## What landed

T2.4 depended on T1.2 (profile/setup-status contract) and T2.1–T2.3 (real
model catalog/install/selection), all done, plus the T3.1 design-system
foundation, also done. Landing the actual four setup screens exposed that
`setup_status_handler`'s `next_step` derivation was still on T1.2's original
interim bridge (a legacy-detected, currently-ready backend satisfying "model
ready", per its own explicit comment) and that nothing anywhere persisted
`selected_model_id`/`selected_model_version` — both named as owed migrations
in the T1.2/T2.3 evidence docs. Closing those was a prerequisite for building
real setup screens against real state, not a separable follow-up, so this
task is backend + frontend together.

### Backend (`src/samosa_gateway.c`)

- **`profile_set_selection(g, model_id, version)`**: persists "the user
  selected this model" the moment an install is accepted
  (`models_install_handler`) or a backend switch is accepted (`POST
  /v1/backends/select`) — not gated on readiness, matching §5.1's "Starting
  an install or selecting an installed model persists the selected
  model/version" verbatim. `POST /v1/backends/select` gained an optional
  `model_version` body field so a caller with the catalog's real version
  string in hand (the new Model view) persists that instead of nothing;
  omitted, it keeps whatever version was already on record for that same
  model_id rather than guessing.
- **`setup_status_resolve(g, p, out_next_step, out_profile_complete)`**:
  retires the T1.2/T1.4 interim bridges for the model-related steps,
  implementing §5.1's ordered rule against real state:
  1. a nonterminal or recoverable-failed install job for the selected
     model_id → `download` (a job is "recoverable" unless its error code is
     `artifact_not_downloadable` — no download host exists at all, e.g.
     Qwen ahead of a public release host, and retrying cannot fix that);
  2. otherwise, no selected model verified installed+compatible → `model`;
  3. verified but not the live, ready backend (or a selection is still in
     flight) → `download`;
  4. verified + live + ready → `chat`.

  It also carries forward the **legacy-install adoption** the old bridge
  existed for: if `selected_model_id` is still empty but a backend is
  already installed and ready (an existing dogfood install predating any
  onboarding), it's adopted as the implicit selection and persisted —
  **using the catalog's real version string**, not the T1.4 bridge's
  filename basename, fixing the exact debt flagged in the T1.2 evidence doc.
  A forward reference to the InstallJob/SelectionJob types and catalog
  helpers this needs (all defined later in this file) is why the function
  body lives after them with only its prototype forward-declared near the
  top, next to this file's other forward declarations — `setup_status_handler`
  itself is unchanged in position.
- **`GET /v1/setup/status`** now also reports the live `active_install_job_id`
  (previously hardcoded `null` — a gap disclosed, not fixed, in the T2.2
  evidence doc) alongside the already-live `active_selection_operation_id`,
  so a reloading client can reconnect to an in-flight download with no job id
  of its own to have lost.
- **`install_jobs_repair_after_restart(g)`**: called once at startup, before
  the gateway serves any request. A job persisted mid-transfer
  (queued/downloading/verifying/installing) when the *previous* process died
  has no worker thread left to ever move it out of that state — repairs it
  to `paused` (the same safe, resumable state an explicit pause already
  produces) with an honest event explaining why, rather than leaving it
  falsely claiming forever-frozen progress that no future pause/resume/cancel
  call could act on either (they all gate on `g->active_install_job_id`,
  which starts empty every launch).

### Frontend (`assets/app.html`)

Four setup views (`#setup` with `#setupViewName`/`#setupViewWelcome`/
`#setupViewModel`), matching §4.1–4.3's copy and actions, full-screen with no
sidebar/topbar, using the T3.1 token set (no new colors/radii introduced).
`.shell` and `#setup` are both `hidden` by default in markup so nothing
flashes before the first status fetch resolves; both need an explicit
`[hidden]{display:none}` override since they declare their own `display`
value (the exact bug class T3.1's evidence doc already found and fixed twice
elsewhere in this file — audited for here too rather than reintroduced).

- **`refreshSetup()`** is the single entry point for every transition —
  initial load, the 1.5s poll timer while on the Model view, and every
  action handler all call it rather than maintaining separate view-selection
  logic. It fetches `GET /v1/setup/status`, maps `next_step` to a view via
  `setupViewForNextStep()` (`download` collapses into the `model` view — the
  spec's four setup views, not five; download UI lives inside the Model
  view per §4.3), and either shows/updates that view or calls `enterChat()`
  exactly once. Because every decision is re-derived from the server on
  every call, "detect and skip completed steps" and "refreshing resumes
  exact state" are the same code path as ordinary progress, not a special
  case — no client-stored job id or step flag survives a reload.
- **Model view**: cards built from `GET /v1/models/catalog` +
  `GET /v1/models/installs`, correlated per model via `installForModel()`
  (prefers `setup/status`'s live `active_install_job_id`, else the most
  recently updated job for that model_id). `modelCardState()`/
  `modelCardActions()` derive progress/status/available actions per model
  from combined catalog+job+selection state; recovery copy for every
  documented install error code
  (`download_failed`/`size_mismatch`/`checksum_mismatch`/
  `insufficient_space`/`artifact_not_downloadable`/`catalog_invalid`/
  `model_not_found`/`activation_failed`) and every selection error code
  (`backend_start_failed`/`backend_crashed`/`readiness_timeout`/
  `fingerprint_mismatch`/`registry_commit_failed`) is a plain-language
  mapping, not the raw code; only `artifact_not_downloadable` omits a Retry
  button (retrying literally cannot help — no host exists), mirroring
  `setup_status_resolve()`'s own recoverability rule server-side. Download/
  Pause/Resume/Cancel/Retry call the T2.2 install endpoints; "Use this
  model" calls `POST /v1/backends/select` with the catalog's real
  `model_version`.
- Cards are built via `document.createElement`/`textContent` composition,
  not `innerHTML` + string interpolation — every field is server-sourced
  (catalog, job state) but this avoids the escaping question entirely rather
  than relying on it, and keeps the DOM-fixture test able to exercise real
  node structure with the same minimal fake `Element` class
  `tests/test_model_catalog_ui.mjs` already established.

## Acceptance

- **"A clean profile completes the entire flow using a tiny fake model
  fixture."** Verified against the real compiled gateway with a real
  installable fixture artifact end to end: name → welcome → install →
  verified-not-yet-active (`download`) → `POST /v1/backends/select` → `chat`,
  including the persisted `selected_model_version` matching the catalog's
  real value, not a filename (`tests/test_setup_flow.sh` scenario 6, and the
  manual real-catalog smoke test below).
- **"An existing valid model reaches Chat without a download."** Legacy-
  install adoption verified: a pre-placed, real bonsai fixture with no prior
  onboarding reaches `next_step: chat` directly and the adopted version is
  the catalog's real string (scenario 5).
- **"Browser refresh/close/reopen during download resumes exact state."**
  Structural, not simulated: `refreshSetup()` never reads a client-stored job
  id — it always re-derives the view and the in-flight job from
  `GET /v1/setup/status` fresh, which is exactly what a reload would also do.
  Additionally hardened one level further than the acceptance item asks:
  a job orphaned by a **gateway** restart (not just a browser reload)
  mid-transfer is repaired to `paused` rather than left claiming frozen
  progress forever (scenario 7).
- **"Keyboard-only and screen-reader navigation can complete setup."** Each
  view moves focus to its primary control on show (name input, Continue,
  first meaningful action); errors/banners use `role="alert"`; the model
  list uses `aria-live="polite"`. **Not verified with a real screen reader**
  (no such tool in this environment) — this is a structural claim, not a
  measured one; disclosed rather than asserted as tested.
- **"No setup view exposes the normal sidebar prematurely."** `.shell` is
  `hidden` in markup and stays `hidden` until `enterChat()` runs, which only
  ever fires once `next_step === "chat"`.

## Real bugs found and fixed before landing (not disclosed simplifications —
genuine defects that testing this task caught)

1. **The gateway's listening socket had no `FD_CLOEXEC` (`src/samosa_http.h`,
   pre-existing, not introduced by this task).** Every forked child — a
   qwen/bonsai/ornith backend engine, or T2.2's curl download subprocess —
   inherited it across `execve()` and kept it open for as long as that child
   lived. Found for real by `test_setup_flow.sh`'s restart-repair scenario:
   killing the gateway mid-download left a **curl** process (not the
   gateway) holding the listener, and the freshly restarted gateway's
   `bind()` failed with `EADDRINUSE` even though the old gateway process had
   fully exited. This is a real production concern, not just a test
   artifact — any real restart (crash, manual kill, a future launchd
   supervision) while a backend engine or a download is alive would hit the
   same failure to rebind. Fixed with one `fcntl(listener, F_SETFD,
   FD_CLOEXEC)` right after the socket is created.
2. **A killed install job was misreported as a real download failure.**
   Once (1) was fixed, restarting mid-download still corrupted the resumed
   file (`size_mismatch`) because the *old* process's curl child survived
   the kill and kept writing to the same staged file while the *new*
   process's resumed curl also wrote to it. Fixed with
   `install_worker_stop_for_shutdown()`: on shutdown, sets the same stop
   signal `models_install_pause_handler()` already uses (so the worker
   thread treats the kill as an intentional pause, not curl failing) *before*
   sending `SIGTERM`, then polls the shared pid variable rather than calling
   `waitpid()` itself — the worker thread's own `install_run_curl()` already
   owns a blocking `waitpid()` on that exact pid, and reaping it a second
   time from a different thread would race for the same child and risk
   signaling a pid the kernel had since recycled for something unrelated.
   Verified stable across three consecutive full runs of
   `tests/test_setup_flow.sh` after the fix.
3. **My own test fixture's `SERVER_PORT` (18997) coincided with
   `SAMOSA_BACKEND_PORT` (`PORT+1`, also 18997)**, a port a real backend
   process (the fake bonsai server used in scenario 6) binds to. Not a
   product bug — a test-authoring bug found while chasing (1) — fixed by
   picking a `SERVER_PORT` with no numeric relationship to `PORT`.

## Not done / disclosed gaps

- **No real interactive click-through.** This environment has no browser-
  automation tool and no display/screenshot access at all (confirmed
  directly in T3.1's own evidence — `screencapture` produces no file here).
  Every acceptance item above that would normally want a screenshot or a
  real click-through is instead verified structurally (server-driven state,
  no client-side special-casing) or via the DOM-fixture/integration tests
  described above. This is the same constraint every prior UI task in this
  program has hit and disclosed the same way — not attempted differently
  here on the assumption it might work this time.
- **No real screen-reader pass.** The accessibility acceptance item is met
  structurally (focus management, `role="alert"`, `aria-live`) but not
  measured with an actual screen reader, since none is available here.
  T3.4 (the dedicated responsive/accessibility gate) is where a real pass
  belongs.
- **The "offline" recovery item is generic, not per-failure-mode UI.** A
  failed `GET /v1/setup/status` (can't reach the gateway at all) shows one
  shared banner with no per-request distinction; this matches what's
  actually knowable client-side (a fetch that never got a response carries
  no error code to differentiate) and is not a shortfall against the spec,
  which only asks for *a* recovery path, not a taxonomy of unreachable-server
  causes.
- **Paused/failed/canceled install jobs from before this task's own retry-vs-
  no-retry distinction existed are unaffected** — `installErrorRetryable()`
  is purely a rendering decision over the same `error.code` the server
  already reported; no migration was needed or performed.
