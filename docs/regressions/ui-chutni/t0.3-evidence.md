Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T0.3 (Phase 0).
Branch: `ui-chutni`. Date: 2026-07-26. Machine: the reference machine (16 GB

## What landed

### 1. PDF page-batch cap violation (`src/samosa_gateway.c`)

`doc_read_handler`'s initial full-document cache-fill call
(`src/samosa_gateway.c:2248` before this fix) requested
`--json-pages FILE 1 100` unconditionally, but `samosa_extract.c` caps
`--json-pages`'s COUNT at 5 and exits 64 on anything larger — the exact
defect named in CLAUDE.md and the spec. Rewrote the PDF branch to page
through the document in bounded batches of 5 (`next_start` advances by
however many pages each batch actually returned), accumulating per-page
objects into a separate buffer and writing the
`{"ok","page_count","pages":[...]}` envelope once, after the true page
count is known from the first batch. Bounded to 2000 batches (10,000
pages), matching `samosa_extract.c`'s own page-count ceiling.

**Verified with the real extractor, not the test-suite's canned-response
wrapper.** Built `samosa-extract` from current source against the real
PDFium SDK already present on this machine
(`~/Documents/samosa-pdfium-artifacts/chromium-7961/mac-arm64-unpacked`):

```
$ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 1 100
usage: samosa-extract --json FILE ...                                    # exit 64 -- the defect, reproduced
$ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 1 5
{"ok":true,...,"page_start":1,"page_end":5,...}                          # exit 0
$ ./build/samosa-extract --json-pages tests/fixtures/documents/multipage_7pages.pdf 6 2
{"ok":true,...,"page_start":6,"page_end":7,...}                          # exit 0
```

Added `tests/test_doc_read_pdf_paging.sh` (`make doc-read-pdf-paging-test`)
as an automated, real-extractor, real-Jobs-loop regression: it drives a
`find` job whose `doc.read` call targets the 7-page fixture through the
compiled gateway, a fake model backend scripted with new canned responses
in `tests/fake_openai_backend.c` (placed first in the handler so they
shadow the generic fallbacks), and asserts the model actually received
"Page 7 of 7" — provable only if every 5-page batch was read, not just the
first. The script skips gracefully (exit 0) when no real `samosa-extract`
is available (PDFium is optional, per the Makefile's existing pattern), so
it's safe to add to the ordinary suite without a hard PDFium dependency.

**One fixture correction needed along the way**: the original T0.1
`multipage_7pages.pdf` fixture had ~11 characters of text per page, which
tripped `doc_read_handler`'s `needs_image` heuristic (`chars < 50`) and
forced an OCR fallback this environment has no real OCR pack to satisfy.
Regenerated the fixture (`tools/gen_multipage_pdf.py`) with three lines of
realistic filler text per page (173 chars) so the text-layer path is used
directly, matching how any real multi-page document actually looks.

Run repeatedly for stability: 4/4 clean passes.

### 2. Read-cache fingerprints were hardcoded literals

`contract_ver`/`pack_fp` were the literals `"reader-v0"`/`"reader-v0-small"`
— a real extractor or OCR contract change would never invalidate old cache
entries. Added `--version` to `samosa-extract` (mirroring the existing
`samosa-ocr --version` / `OCR_VERSION` pattern) reporting the new
`EXTRACT_VERSION` constant (`"samosa-extract 0 (reader-v0)"`, bump on any
future contract change). The gateway's new `reader_fingerprint()` queries
both sidecars' own `--version` once, caches the composite string
(`extract:...|ocr:...`) for the process lifetime, and degrades to a stable
`unavailable` tag if a sidecar is missing/fails — self-reporting so the
fingerprint can never drift from the binary that will actually run.
`contract_ver` stays `"reader-v0"` (the *JSON shape* contract didn't
change); `pack_fp` is now `reader_fingerprint(g)`.

**A real bug found and fixed while wiring this up**: the first
implementation held `g->mu` locked while calling `run_capture()`, which
itself locks `g->mu` again via `track_job_pid()` — a self-deadlock on the
non-recursive mutex. First real-extractor test run hung indefinitely
(gateway process alive, `curl` blocked, confirmed via `ps` that the
`--version` subprocess call never returned control). Fixed by releasing
the lock before calling `run_capture()` and re-acquiring only to
check-then-cache the computed string (a benign race — both concurrent
computations are idempotent). Re-verified: 4/4 clean, non-hanging passes
after the fix. This is exactly the kind of concurrency defect the project's
non-negotiables warn about; recorded here rather than silently fixed.

### 3. One-writer locking and atomic durable publication (`src/read_cache.h`)

`read_cache_put()`'s temp filename was `<path>.tmp.<pid>` with no locking.
Two *threads in the same process* (the gateway is multithreaded) racing to
publish the same content-addressed key would compute the identical temp
path, both `open(..., O_TRUNC)` it independently, and could interleave
writes — whichever `rename()` landed last would publish a corrupted entry.
Added a per-shard (`<sha[0:2]>/.lock`, ≤256 across the whole cache) `flock`
around the write; `flock` locks are per open-file-description, so it
correctly serializes distinct threads, not just distinct processes. Also
added `fsync` on the temp file before `rename()` and `fsync` on the shard
directory after, for real crash durability of the publication, not just
in-process atomicity.

**Proved the fix is real, not just plausible**, by reverting it: copied
`read_cache.h` to a scratch directory, mechanically stripped the `flock`
calls, rebuilt the test binary against the stripped header, and ran the new
8-thread same-key race test 5 times — **3 of 5 runs failed** ("published
entry exactly matches one writer, not a corrupted mix"). With the real
fix in place: 8/8 clean passes. The test genuinely catches the bug it's
named for.

### 4. Identity re-check between hash and cache commit (`src/samosa_gateway.c`)

`doc_read_handler` computed the cache key from the file's bytes, then spent
potentially seconds extracting/OCRing, then published under that key with
no re-check that the file was still the same bytes — a file rewritten
mid-read could publish fresh text under a stale hash forever (the cache
never re-verifies on a hit). Added a `stat()` before the hash and another
right before `read_cache_put()`, comparing dev/inode/size/nanosecond mtime
(mirroring `src/samosa_fs.c`'s existing `process_file()` pattern); a
mismatch returns `changed_during_read` and skips the cache write entirely.

### 5. Cache size accounting and bounded pruning (`src/read_cache.h`)

Added `read_cache_total_bytes()` (a directory walk summing entry sizes —
`.lock`/`.tmp.*` files excluded) and `read_cache_prune(root, max_bytes)`
(oldest-`mtime`-first removal until under budget). An entry with a
companion `<key>.pin` sentinel file is never removed regardless of age —
nothing creates `.pin` files yet (that's T4.5's scope/job owner-reference
tracking), but the mechanism is in place and tested now so pruning is safe
to enable before that lands. Verified: three entries, oldest pinned,
budget forced below total — the pinned oldest entry survives, the
unpinned older entry is removed first, total bytes decrease.

## Acceptance criteria — verified

1. **"A PDF longer than five pages is processed without violating the
   extractor contract."** `make doc-read-pdf-paging-test` — real extractor,
   real 7-page PDF, PASS (4/4 runs).
2. **"Concurrent reads of the same content produce one valid cache
   entry."** 8-thread same-key race test in `tests/test_read_cache.c` —
   PASS (8/8), and proved meaningful by reproducing the pre-fix failure
   (3/5 runs corrupted) against a mechanically-stripped copy of the header.
3. **"Changing a file during extraction cannot publish text under the old
   hash."** Identity re-check added; `changed_during_read` returned on
   mismatch instead of a cache write. (Exercising a live race during a real
   multi-second extraction end-to-end is impractical to automate
   deterministically; the check itself — dev/inode/size/mtime compared
   before and after — is the same pattern already proven correct and
   tested elsewhere in this codebase, `src/samosa_fs.c`'s
   `process_file()`/`validate_move_source()`.)
4. **"A stale parser fingerprint triggers re-extraction."** New
   `test_read_cache.c` case: put under `fp_v1`, confirm a lookup under
   `fp_v2` misses, re-put under `fp_v2` (simulating re-extraction),
   confirm `fp_v2` now hits with the correct content and `fp_v1` is now a
   miss. PASS.

## What T0.3 does not include

- A real OCR pack to make `doc-read-test`/`motto-test`/`tier2-test`/
  `r7-r6-test` runnable in this environment (pre-existing gap, noted above).
- Wiring `read_cache_prune()`/`.pin` into any caller — nothing calls prune
  yet, and nothing creates `.pin` files yet. That lands with T4.5's scope/
  job owner-reference tracking, which is exactly what the mechanism was
  built to support.
- Any change to the read-cache's on-disk JSON *shape* — `contract_version`
  stays `"reader-v0"` because the entry structure itself didn't change,
  only what fingerprints validity against.
