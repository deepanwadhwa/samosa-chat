## Container target (root `Dockerfile`)

**Status: currently broken — verified 2026-07-25 by static inspection, not a live build.**

The `Dockerfile` at the repo root (last touched 2026-07-19, commit `31c1941`)
still does:

```dockerfile
COPY tools/samosa_gateway.py /release/bin/samosa-gateway
COPY tools/samosa_models.py /release/bin/samosa_models.py
```

Both source files were removed from the repository when Gate 11 replaced the
Python jobs/gateway stack with the native C gateway (`src/samosa_gateway.c`) —
confirmed by `ls tools/samosa_gateway.py tools/samosa_models.py` returning "No
such file or directory" on this branch. A `docker build` on this Dockerfile
today would fail at the first of those two `COPY` layers, before ever
reaching the compiled `qwen36b` engine stage. **A full `docker build` was not
run** — the local Docker daemon is not running in this environment
(`docker build` failed with "Cannot connect to the Docker daemon"), so this is
a static-file-existence finding, not a reproduced build failure. The static
evidence (two `COPY` sources provably absent) is sufficient on its own: a
`COPY` of a nonexistent source path is an unconditional Docker build error,
not a maybe.

This means: **"native-local" and "container" are not two equally-supported
packaged targets today.** Only native-local (macOS arm64, Linux x86_64/
aarch64 via `install.sh`) currently produces a working install. The container
path needs its own repair (out of scope for this UI/Chutni program — it
belongs to issue #2/Windows-Docker) before "container" can appear as a real
row in a future revision of this matrix. Recorded here because T1.0/T1.1
("model-free browser runtime package") explicitly touches `dist/samosa`,
`tools/package_hf.py`, and container release assembly, and an agent working
that task needs to know the container path does not build at all right now —
independent of anything this program changes.

## Browser versions

**Not verified — no automated browser test infrastructure exists in this
repository today.** Confirmed by inspection: no headless-browser runner,
no Playwright/Selenium/Puppeteer config, and no CI browser matrix anywhere
under `tests/`, `tools/`, or `.github/` (if present). `docs/UI_DESIGN.md` and
`docs/TASKS_UI_CHUTNI.md` T3.4/T7.3 call for "the exact latest/previous-stable
Safari, Chrome, and Firefox builds" but that list has never been filled in
with real, dated version numbers because nothing has run the app in a browser
under test control yet. **This row must be completed as part of T3.4**, using
whatever Safari/Chrome/Firefox versions are actually installed on the
reference machine at the time that gate runs, named explicitly (not "latest").
Until then, any claim of specific browser support in user-facing docs would be
an unmeasured claim and must not be made (CLAUDE.md non-negotiable: "never
overstate platform support").

## What this matrix is for

Per T0.1's acceptance criterion, this file is the frozen ground truth
`docs/TASKS_UI_CHUTNI.md` acceptance/release-gate language should defer to
when it says "actually packaged targets." Update it in place as later tasks
change what's actually shipped (e.g., if the container path is repaired, or
T3.4 fills in real browser versions) — do not let a second, drifting copy of
this table appear elsewhere.
