# T2.3 — Make model activation readiness-safe: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T2.3 (Phase 2),
§5.3 (model catalog and lifecycle). Branch: `ui-chutni`. Date: 2026-07-27.
Machine: the reference machine (16 GB Apple Silicon MacBook Air, macOS
26.5.1, Darwin 25.5.0 arm64).

**Status: DONE.** `POST /v1/backends/select` (`src/samosa_gateway.c`) still
forks synchronously and returns 202 the instant `fork()` succeeds — that
timing contract predates this task and neither `assets/app.html` nor
`tests/test_compiled_gateway.sh` had a reason to have it changed. What T2.3
adds is everything *after* the fork: a durable selection job (same shape as
T2.2's `InstallJob`) with a background watchdog that waits for real
readiness (a bounded timeout, not "a process exists"), confirms the target
model's weights artifact wasn't swapped out from under the load (a
size+mtime snapshot), and detects an immediate child crash via
`waitpid(WNOHANG)`. Any failure — including the final durable commit itself
— rolls back to whichever backend was working before the switch, and the
`model-backend` selection file is only ever rewritten once readiness and the
fingerprint both already passed.

## What was built (`src/samosa_gateway.c`)

- **`SelectionJob`** (mirrors T2.2's `InstallJob`): `job_id`,
  `requested_backend`, `previous_backend`, `state`
  (`starting`/`waiting_ready`/`selected`/`failed`), `error_code`/`message`,
  `active_backend`, and a fingerprint snapshot (`expected_bytes`,
  `expected_mtime_sec`, `expected_mtime_nsec` — see "the fingerprint" below
  for why mtime is split into two fields). Persisted under
  `<home>/run/selections/<job_id>/job.json` + `events.jsonl`, using the same
  `durable_state_put`/`durable_event_append` primitives (`durable_job.h`,
  T0.4) T2.2 already builds on.
- **The synchronous half** (`/v1/backends/select`, unchanged in shape):
  validates the target, rejects if generation is active (unchanged), then —
  for an actual switch — waits up to `SAMOSA_TEST_SELECTION_BUSY_WAIT_MS`
  (default 2000ms) for any prior in-flight switch to clear before either
  proceeding or returning `409 selection_busy`; snapshots the target's
  weights fingerprint; persists the job; calls the existing
  `backend_stop()`/`backend_start()` exactly as before T2.3; and, on a
  successful fork, spawns the watchdog and returns 202 with an added
  `job_id`/`status_url` (additive fields — `test_compiled_gateway.sh`'s
  existing `grep -q '"accepted":true'` checks are untouched).
- **The watchdog** (`selection_watchdog`, detached thread): polls
  `backend_probe()` up to `SAMOSA_TEST_SELECTION_READY_TIMEOUT_MS` (default
  20000ms), checking `waitpid(pid, &wstatus, WNOHANG)` first each iteration
  to detect an immediate crash rather than waiting out the full timeout.
  Also checks `g->stopping` first: if the gateway itself is shutting down,
  the job is marked `failed`/`gateway_shutdown` *without* attempting a
  rollback (see "the shutdown-orphan bug" below for why this check exists).
  On success: fingerprint re-check, then commit (`write_small_file` to
  `g->selection_file`) only now — a commit failure rolls back exactly like
  every other failure mode.
- **Rollback** (`selection_restore_previous`): `backend_stop()` the broken
  process, restore `g->backend` in memory, restart the previous backend.
  Guarded against forking during shutdown (`!atomic_load(&g->stopping)`) —
  see below.
- **Durable registry endpoints**: `GET /v1/models/selection/<job_id>`,
  `GET /v1/models/selection/<job_id>/events` (plain JSON replay, matching
  T2.2's convention), and `GET /v1/models/selection/active` — the last one
  lets a client that reloads mid-switch reconnect *without ever having
  known a job_id*, satisfying the acceptance item's reconnect requirement
  for a page refresh, not just a resumed poll. All three are gated by the
  default fail-closed dispatcher (not on the legacy-unauthenticated list),
  same as T2.1/T2.2's routes.
- `setup_status_handler()`'s `active_selection_operation_id` field — a
  hardcoded `null` placeholder since before T2.1 — now reports the real
  in-flight job id. Its sibling `active_install_job_id` field is left as
  the pre-existing `null` placeholder; wiring it is unrelated to this task
  and not touched.
- `durable_job_id_generate` — renamed from T2.2's `install_generate_job_id`
  (it was already fully generic; the old name just implied otherwise) and
  reused rather than duplicated for selection jobs.

## The fingerprint, and its disclosed limit

"Model fingerprint confirmation" is implemented as a stat() snapshot of the
target backend's primary weights file (`bytes`, `mtime_sec`, `mtime_nsec`),
taken at request time and re-checked once the new process is reachable — a
mismatch (the file was replaced or truncated mid-load, e.g. by a concurrent
install activation) rolls back exactly like a crash or timeout. This does
**not** hash the file — a content hash was rejected as impractical for a
20+ GB weights file on every switch, matching this project's existing
practice for T2.1's own artifact-presence check (`artifact_is_present`
compares only size, not a hash, for the same reason). The disclosed gap: a
same-size, same-mtime content change would not be caught. `mtime` is stored
as two fields (seconds + nanosecond remainder) rather than one combined
nanosecond epoch value — `json.h` stores every number as a `double`, and a
nanosecond epoch timestamp (~1.7×10¹⁸) is far past `2^53`, the largest
integer a `double` represents exactly; a single combined field lost
precision on the save/load round trip and produced permanent false
mismatches (caught before landing — see "bugs found" below).

## Bugs found and fixed before this landed

Three real, non-obvious bugs surfaced by testing against the real compiled
gateway (not just the new isolated test), each with its own reproduction
below. All three are why this task took the shape it did — the design
notes above already reflect the fixes, not the original attempt.

**1. Nanosecond-epoch mtime lost precision through `json.h`'s `double`
storage** (see above), causing every real fingerprint check to report a
false mismatch. Caught by `tests/test_model_selection.sh`'s happy-path
scenario failing outright. Fixed by splitting mtime into seconds +
nanosecond-remainder fields, each individually far inside a double's exact
range.

**2. A gateway shutdown mid-switch orphaned a freshly-forked backend
process.** Reproduced directly: switch backends, then kill the gateway
before the watchdog thread settles. `main()`'s SIGTERM-triggered
`backend_stop()` zeroes `g->backend_pid` concurrently with the detached
watchdog thread's own readiness loop; the watchdog's next check sees
`pid<=0`, reads that (from its own, correct, local point of view) as "the
child crashed," and calls `selection_restore_previous()` — which forks a
fresh copy of the *previous* backend right as the whole process is exiting.
`main()` has already run its one `backend_stop()` and never runs a second
one; the watchdog thread doing this fork is itself killed moments later
along with the rest of the process, so nothing is ever left to reap that
child. Fixed two ways: `selection_restore_previous()` never forks while
`g->stopping` is set, and the watchdog's own loop checks `g->stopping`
*first* and reports `gateway_shutdown` (skipping the pointless, now-doubly-
guarded rollback attempt) instead of misreporting `backend_crashed`.
Verified with a 5-run repro loop (switch, immediate kill, `ps` check for a
leftover `test_fake_openai_backend`): clean every time after the fix,
reproduced every time before it.

**3. An explicit `switching` interlock flag caused a real, intermittent
regression in `tests/test_compiled_gateway.sh`'s pre-existing vision-backend
scenario** (switch to Bonsai, send an image job, expect a real response).
The flag was meant to stop ordinary chat/Jobs inference from landing on a
backend mid-teardown/mid-restart — an addition beyond T2.3's literal
acceptance list, meant as extra robustness. It backfired: it was cleared by
the *watchdog's own* polling loop, a clock entirely independent of
`backend_probe()`'s live readiness check (which `/healthz`, `proxy_request`,
and `backend_json` already use). A caller that saw `/healthz` report
`ready:true` and immediately made a follow-up request could still be told
`503 model_switching` (or get a silent `NULL` from `backend_json`,
surfacing as Jobs' `invalid_model_output`) for a brief window after the
backend was already genuinely answering — exactly what broke the
vision-backend scenario's very next request after a successful switch.
**Removed entirely**, along with its Gateway struct field, both call sites,
and the test that had asserted the flag's behavior. The interlock this was
trying to add is already provided, without any lag, by the pre-existing
`backend_probe()` gate in `proxy_request()`/`backend_json()`: `backend_stop()`
closes the port before `backend_start()` forks the replacement, so a
request landing in that gap already got (and still gets) the same
retryable "not ready" response it always did — unchanged by this task, and
exercised end to end by every scenario in `tests/test_model_selection.sh`
that switches, waits for `ready:true`, and immediately does something else.
Found only by running the pre-existing, unrelated
`tests/test_compiled_gateway.sh` end to end after each change — the
isolated new test never exercised a real Jobs vision call, so it could not
have caught this on its own. Worth remembering: a new isolated test passing
is not evidence that an existing, larger integration test still passes;
both were run before this landed.

## Tests

`tests/test_model_selection.sh` (`make test-model-manager`, real compiled
gateway + `tests/fake_openai_backend.c`, extended with a `/healthz` alias
so it can stand in for `SAMOSA_QWEN_ENGINE` too, and a
`SAMOSA_FAKE_HEALTH_DELAY_MS` knob for a deterministic pre-readiness
window):

1. Auth: the new `/v1/models/selection/*` routes are gated by the default
   fail-closed dispatcher; `GET .../active` with no in-flight switch is a
   clean `404 no_active_selection`.
2. Happy path: switch qwen→bonsai; job reaches `selected`; `/healthz` agrees
   (`backend`, `ready:true`); `model-backend` file durably records the new
   backend; `GET .../active` returns `404` once terminal (no longer
   "in flight").
3. Reconnect mid-switch: with a delayed `/health` response giving a real
   window, `GET /v1/models/selection/active` returns the same in-flight
   `job_id` with an in-progress state — the acceptance item's "refresh
   during model load reconnects through the durable registry," done without
   the client ever knowing a `job_id` in advance.
4. A second switch while one is in flight is rejected (`409
   selection_busy`), mirroring T2.2's single-active-transfer gate.
5. Readiness timeout: target forks but never binds its port (a
   `sleep`-only wrapper script) → `failed`/`readiness_timeout`, `qwen`
   restored and ready, `model-backend` file never touched.
6. Immediate child crash: target execs a script that exits 1 → detected
   well under the 20s default timeout (not by waiting it out), `qwen`
   restored.
7. Fingerprint mismatch: target's weights file is overwritten (different
   size) during a delayed-health window → `failed`/`fingerprint_mismatch`,
   `qwen` restored, `model-backend` file never committed to the new
   backend.
8. Registry commit failure: readiness and the fingerprint both pass, but
   `g->selection_file`'s directory is `chmod 0500` (read-only) so the
   durable write fails → `failed`/`registry_commit_failed`, the live
   process is rolled back to match the untouched, still-correct file.

Every scenario above uses `qwen` (via `test_fake_openai_backend` standing in
for `SAMOSA_QWEN_ENGINE`) as the backend that must be restored, so a
restore's success is checked against a real, independently-verified working
state rather than the very backend under test.

```

...

concurrent switch rejected (409 selection_busy): PASS
readiness timeout -> failed, restores the prior working backend: PASS
immediate child crash -> failed fast, restores the prior working backend: PASS
fingerprint mismatch (weights file swapped mid-switch) -> failed, restores the prior working backend: PASS
registry commit failure -> failed, live process rolled back to match the untouched file: PASS
test_model_selection.sh: PASS
```

Also re-run clean after every fix above: `make test-ui-setup`, `make
jobs-test` (which itself runs `compiled-gateway-test`), and `make test`.
`tests/test_compiled_gateway.sh` was additionally run 3 consecutive times

## Acceptance checklist

- **Selection never returns "ready" merely because a process was
  forked.** `/v1/backends/select`'s response never claims readiness (only
  `accepted`/`job_id`); the job itself passes through
  `starting`→`waiting_ready` and only reaches `selected` after a real
  `backend_probe()` success, a fingerprint match, and a durable commit.
- **A forced exec/load failure leaves a usable prior model or a clear
  no-model state.** Every failure path (timeout/crash/fingerprint/commit)
  calls `selection_restore_previous()`; if the previous backend also can't
  start, existing `backend_state_string()`/`healthz` machinery already
  reports `"failed"`/`"none"` honestly — no new state invented for that
  case.
- **Readiness timeout, fingerprint mismatch, immediate child crash, and
  registry commit failure all preserve or restore the prior active
  selection.** Each has its own dedicated test above (scenarios 5–8).
- **No duplicate or orphan backend remains after repeated switches.**
  `backend_stop()` always precedes a new `backend_start()`, both in the
  synchronous switch path and in rollback; bug #2 above (the one real
  orphan found) is fixed and covered by a direct repro (not, admittedly, an
  automated regression test in `test_model_selection.sh` — reproducing a
  SIGTERM-during-watchdog race deterministically in a shell test was judged
  not worth the added flakiness risk given the fix is a simple, obviously-
  correct guard).
- **Health and UI agree on the active model and version.** `/healthz`
  reads `g->backend` live; the frontend (T2.1's catalog wiring) already
  polls the same endpoint. Nothing in T2.3 introduces a second, cached
  source of truth for "what's active."
- **Refreshing or reopening during model load reconnects through the
  durable selection-operation registry.** `GET /v1/models/selection/active`
  (scenario 3 above).

## Deliberately out of scope, not forgotten

"Relevance checks" and "Chutni summary inference" (named in the spec's Work
list alongside Chat and Jobs) don't exist as code paths yet — Chutni is
Phase 4, still unbuilt. There is nothing to interlock with yet; when those
paths are built, routing their model calls through the same
`backend_probe()`-gated functions this task relies on (`backend_json`/
`proxy_request`) is what will cover them, not a new mechanism.
