# T0.2 — Make scanning safe and streaming: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T0.2 (Phase 0).
Branch: `ui-chutni`. Date: 2026-07-26. Machine: the reference machine (16 GB
Apple Silicon MacBook Air, macOS 26.5.1, Darwin 25.5.0 arm64 — same as T0.1).

## What landed

Added two new `samosa-fs` commands, alongside the existing `survey`/`list`/
`metadata`/`move`/`undo` (all unchanged):

- **`samosa-fs chutni-inventory --root ROOT [--include-hidden]
  [--cross-filesystems] [--exclude NAME]...`** — a depth-first, streaming
  walk that emits one NDJSON record per entry to stdout as it is discovered
  (`{"type":"file",...}` or `{"type":"skip","reason":...}`), terminated by
  one `{"type":"done",...}` summary line. Unlike the existing
  `scan_root()`/`collect_paths()` path (which appends every path into one
  in-memory `PathList` and `qsort`s the whole thing before processing
  anything — the exact defect CLAUDE.md and the spec name), this never
  materializes the tree: memory is bounded by directory depth, not total
  file count, because each entry is emitted and discarded immediately.
  Content is never read — no hashing, no magic-byte typing — matching the
  spec's "hash only when requested" principle; typing/extraction is deferred
  to T4.2/T4.3.
- **`samosa-fs chutni-hash --root ROOT PATH`** — the only place a Chutni scan
  reads file content, and only for one already-inventoried path on explicit
  request. Always a complete SHA-256 over the whole file (no cap, no
  truncation marker — the exact opposite of the existing `hash_for_scan()`'s
  25 MiB-capped, "cannot prove the un-hashed tail is unchanged" hash), with
  the same no-follow-open + fstat-identity-before-and-after discipline as
  the existing `validate_move_source()`, so a file rewritten mid-hash is
  caught (`changed_during_read`) rather than silently hashed under a stale
  identity.

Mechanics reused directly from the existing file rather than reinvented:
`buf_put`/`buf_printf`/`buf_json_string` (Buffer output), `join_path`,
`has_dotdot_component`/`inside_root_abs` (containment), `stat_mtime`
(cross-platform nanosecond mtime), the existing `Sha256` implementation.

One additive, narrowly-scoped production seam: `SAMOSA_CHUTNI_TEST_DELAY_US`
(an env var, default unset/zero-cost) inserts a per-entry `usleep()` so a
cancellation test can exercise the required two-second stop bound against a
small, fast-to-create fixture instead of needing hundreds of thousands of
real files. Looked up once via a cached static; adds one branch per entry
when unset.

## Acceptance criteria — verified

All six from the spec, each with a direct automated check in
`tests/test_chutni_inventory.sh` (`make test-chutni` — PASS):

1. **"A symlink cannot escape the root."** The walk never opens/descends a
   symlink at all (`S_ISLNK` check immediately after `lstat`, before any
   `open`) — it is recorded as a `symlink` skip and nothing about its target
   is ever touched. Verified against the T0.1 fixture's two escape attempts
   (absolute `-> /etc` and a multi-`../` relative escape also targeting
   `/etc`): both produce a `symlink` skip, and the full inventory output
   contains no reference to `/etc` anywhere — proof nothing was resolved
   into the escape target, not just that the symlink itself wasn't listed
   as a file.
2. **"Duplicate content at two paths yields two path records."** Confirmed
   against the T0.1 fixture's `duplicate/a/receipt.txt` +
   `duplicate/b/receipt-copy.txt` (byte-identical): both appear as separate
   `"type":"file"` records. This holds trivially by construction — unlike
   the legacy `scan_root()`/`add_hash()` path, `chutni-inventory` never
   hashes content at all during inventory, so there is no hash-based
   collapsing to lose the second path.
3. **"An unreadable nested directory is counted and the scan continues."**
   `chutni_walk()` treats a failed `opendir()` (permission denied) as a
   recorded skip (`permission_denied` if `EACCES`, else `unreadable`) and
   `return`s success, not failure — the caller keeps walking siblings. This
   is the literal fix for `collect_paths()`'s current behavior of returning
   `0` (hard abort) on the first `opendir`/`append_path` failure at any
   depth. Verified: the fixture's `chmod 000 unreadable/blocked` produces
   exactly that skip record, and every other file in the tree (including
   siblings of `unreadable/`) still appears in the same run's output.
4. **"An inventory-only unchanged refresh reads metadata but no file
   content."** Verified structurally (no code path in `chutni-inventory`
   ever calls `open()`/`read()` on a regular file) and empirically (grepped
   the full NDJSON output for `sha256`/`"hash"` — absent).
5. **"Memory is bounded by queues/path buffers rather than total file
   count."** No `PathList`/array of all paths is built; each directory's
   entries are consumed one at a time via `readdir()` and either emitted
   immediately (files) or recursed into immediately (subdirectories) — peak
   memory is O(directory depth), not O(file count). (A quantitative RSS
   measurement at real drive scale is T6.3's job, not T0.2's; this task
   verifies the *mechanism* is streaming, which the code structure makes
   inspectable directly.)
6. **"Cancellation stops within two seconds and leaves no published partial
   result."** `g_chutni_canceled` (a `sig_atomic_t` set from a `SIGINT`/
   `SIGTERM` handler) is checked at the top of every directory and before
   every entry, so a signal is noticed within one entry's processing time.
   Verified with the `SAMOSA_CHUTNI_TEST_DELAY_US` seam (2 ms/file, 500
   files, `SIGTERM` sent 0.1 s after start): the process exits well within
   the 2-second bound, the run's terminal line reads
   `{"type":"done","canceled":true,...}`, and the output has fewer than 500
   file/skip lines — i.e., the scan genuinely stopped mid-tree rather than
   completing and racing the signal. "Leaves no published partial result" at
   this layer means exactly this: `chutni-inventory`'s output is a stream
   the *caller* (not yet built — that's T4.2's job) must not treat as a
   complete/published generation unless it ends with `"canceled":false`;
   this task's job is to make that distinction observable, not to implement
   the caller-side publication transaction (T4.2/T4.5).

Two additional mechanisms landed and tested beyond the letter of the six
criteria, both explicitly named in T0.2's own **Work** list:

- **Filesystem-boundary policy**: a directory is skipped
  (`cross_filesystem`) and not descended into when its `st_dev` differs from
  the root's, unless `--cross-filesystems` is passed. Not exercised against
  a *real* second mounted filesystem in this task (none available in this
  environment) — that real-hardware verification belongs to T6.1 ("Drive
  scope"), which explicitly owns "mount-boundary behavior." The mechanism
  itself (the `st_dev` comparison and non-descent) is implemented and will
  be exercised for real once T6.1 has an actual second volume to test
  against.
- **Exclusion policy**: `--exclude NAME` performs an exact, component-name
  match (not substring, not glob) against any path component, skipping with
  `user_exclusion` and not descending if the excluded name is a directory.
  Verified with `--exclude oversized` against the fixture: the directory
  itself is recorded as a `user_exclusion` skip and nothing beneath it
  (`oversized/big.bin`) appears in the output.

No existing `samosa-fs` command (`survey`, `list`, `metadata`, `move`,
`undo`) was modified. The two new commands and their supporting types
(`ChutniPolicy`, `ChutniCounters`, `chutni_walk`, `chutni_emit_file`,
`chutni_emit_skip`, `command_chutni_inventory`, `command_chutni_hash`) are
additive, inserted as a self-contained block between the existing
`scan_root()` and `type_count_add()`. `main()`'s argument parsing gained
three new flags (`--include-hidden`, `--cross-filesystems`, `--exclude`,
the last repeatable) and two new command-dispatch branches; the existing
`move`/`undo`/`survey`/`list`/`metadata` dispatch logic is untouched.

## What T0.2 does not include

- Real cross-filesystem verification (needs an actual second volume — T6.1).
- Mandatory/versioned exclusion *rules* from §6.1 (credential stores,
  Samosa's own state, etc.) — T0.2 built the exclusion *mechanism*
  (`--exclude`); the actual policy table with `mandatory`/`user_overridable`
  kinds and a `policy_fingerprint` is T4.2's job.
- A scope registry, manifest persistence, or SQLite integration — this task
  is purely the sidecar-level scan primitive; T4.2 wires it into a durable
  Chutni scope.
- Quantitative memory/throughput measurement at drive scale — T6.3.
