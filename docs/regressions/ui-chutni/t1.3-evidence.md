# T1.3 — Implement the safe browser directory chooser: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T1.3 (Phase 1),
§5.4 (browser directory chooser). Branch: `ui-chutni`. Date: 2026-07-26.
Machine: the reference machine (16 GB Apple Silicon MacBook Air, macOS
26.5.1, Darwin 25.5.0 arm64).

## What landed (`src/samosa_gateway.c`, `src/samosa_http.h`, `assets/app.html`)

### Query-string plumbing (a prerequisite; nothing consumed it before)

`samosa_http_read_request()` split the query string off `request->path` at
the `?` but never stored it anywhere — it was silently discarded. Added a
`char query[256]` field to `SamosaHttpRequest` and capture the raw (still
percent-encoded) tail there before truncating `path`. This is the first
route in the program that needs a query parameter (`GET
/v1/fs/directories?path=...`); every prior v1 route took its input from the
JSON body.

### `GET /v1/fs/roots`

Returns the real OS user home plus, on macOS, mounted volumes under
`/Volumes`. Added `Gateway.user_home`, populated from `getenv("HOME")` with
a `getpwuid()` fallback — this is deliberately **not** `Gateway.home`
(Samosa's own app-state directory, redirectable via `SAMOSA_HOME` in
tests/containers). Every root is `realpath()`'d once so later containment
checks are plain prefix comparisons against a symlink-free string. Volume
discovery is macOS-only for now; Linux/Windows get Home only. That is an
honestly scoped gap, not a shortcut: the T0.1 capability matrix already
states a container target never offers Drive/This-computer scopes, so
Home-only is correct there, not incomplete.

### `GET /v1/fs/directories?path=<encoded-canonical-path>`

Every request is `realpath()`'d fresh and checked against the **current**
roots list — the client's prior responses are never trusted as proof of
safety, only as a hint of what to ask for again. Listed entries:

- are directories only (files, sockets, FIFOs are never returned — "no file
  contents" per spec);
- exclude symlinks entirely, checked with `fstatat(..., AT_SYMLINK_NOFOLLOW)`
  on each entry before it's ever added to the response, so a symlinked
  subdirectory can never be a later navigation target;
- exclude dot-prefixed (hidden) names outright;
- include a permission-denied child directory with `readable:false` instead
  of omitting it, so the UI can show "unavailable" rather than the caller
  guessing or the chooser silently going quiet.

The directory itself is opened with `O_NOFOLLOW | O_DIRECTORY` after the
`realpath()` + containment check, matching the no-follow-open discipline
`src/samosa_fs.c` already uses for Chutni scanning (T0.2).

## Two real bugs found while building this (not merely designed away)

1. **Root containment silently failed for a root that resolves to `/`.**
   macOS commonly exposes the boot volume under `/Volumes` as a symlink
   *to* `/` (confirmed on this machine: `/Volumes/Macintosh HD` →
   `realpath` → `/`). The prefix check `strncmp(root, path, len) &&
   path[len]=='/'` requires a `/` immediately after the root's own length —
   for root `"/"` (length 1), `path[1]` is never `/` for any real path like
   `/etc`, so the check rejected *every* path under a `/` root except `"/"`
   itself. `src/samosa_fs.c`'s `inside_root_abs()` already special-cases
   `root == "/"` for exactly this reason; I had not copied that special
   case. Fixed by matching it. Caught by an ad hoc curl smoke test
   before the shell test was even written — see "traversal attempt" in the
   scratch commands below, which returned `404` instead of the expected
   `403` and prompted checking *why* rather than accepting a plausible-looking
   status code.
2. **Skip the redundant `/` alias entirely.** Once (1) was fixed, keeping a
   `/Volumes/Macintosh HD` → `/` entry as a first-class chooser root would
   make System/Library/private browsable as if it were "another place to
   store files" — it's the same filesystem Home already lives on. Roots now
   skip a `/Volumes` entry whose `realpath()` is exactly `/`.
3. **`chooserActivateFocused()` didn't await its own navigation.** It called
   `chooserOpenPath(entry.path)` without `await`/`return`, so a caller
   awaiting it (or a future caller checking whether navigation finished)
   would resolve immediately, before the fetch completed. Caught by the DOM
   fixture test (`tests/test_chooser_ui.mjs`), not by inspection — an
   assertion checking `chooser.path` right after `await
   chooserActivateFocused()` failed with the state still `null`. Fixed by
   making the function `async` and awaiting the inner call.

## Frontend (`assets/app.html`)

Added a keyboard-accessible dialog (`role="dialog"`, `aria-modal`,
`aria-labelledby`, a real focus trap cycling only enabled controls, Escape
to close and return focus to whatever opened it, arrow keys / Enter /
Backspace inside the folder list). Styled with the **current** shipped
tokens (`--paper`, `--panel`, `--line`, `--brand`, …), not the newer palette
proposed in `docs/UI_DESIGN.md` — that redesign hasn't landed anywhere else
in `assets/app.html` yet, and styling one new component in the future
language while everything around it stays in the old one would read as
broken, not ahead of schedule.

**Scoping decision, stated plainly**: T1.3 sits outside the
T1.1→T1.2→T2.1→T1.0 and T3.1→T2.4 dependency chains in the spec's own
diagram — it is not wired into the composer's `+` menu or the Chutni
Add-Chutni flow, because neither exists yet (composer attach is still a
single "attach image" button; the `+` menu is T2.4/T3.x work, and Chutni
scope creation is a later Chutni-specific task). Wiring a dialog into UI
surfaces that don't exist yet isn't possible without inventing them ahead of
their own tasks, so the trigger for now is a labeled "Folder access
(preview)" control in the existing Settings panel, with copy that says
plainly it previews the picker and creates no Chutni memory. This also
required adding the `<meta name="samosa-ui-token">` placeholder to
`assets/app.html` (present since T0.1/T1.2 only as a documented gap — "the
current app.html has no such placeholder yet") and a small `authFetch()`
helper, since `/v1/fs/*` is gated by `require_ui_session()` like every new
v1 route. No pre-existing route was retrofitted to require the token.

## Acceptance criteria

- **"`..`, encoded traversal, symlink, and race attempts cannot leave
  allowed chooser roots."** Covered by `tests/test_fs_chooser.sh`: a direct
  request for `/etc` (outside every root) → `403`; a request built from
  `%2e%2e` segments (encoded dots, not literal `..`) walking up past every
  root → `403`, exercising decode-then-validate rather than a raw-string
  `..` filter that encoding could evade; a symlink (`Documents/EvilLink` →
  `/etc`) → `403` when browsed directly, and never appears as an enterable
  entry when its parent is listed. "Race attempts" against the
  realpath-then-open gap are bounded the same way `samosa_fs.c` already
  bounds them (final `open()` uses `O_NOFOLLOW`, so a last-instant symlink
  swap on the final path component fails closed) — this repo does not have
  a full per-component `openat` walk anywhere yet, so this inherits that
  existing limitation rather than closing it; not claiming more than that.
- **"The API returns no file contents."** `notes.txt` placed in the listed
  directory never appears in `directories` (files are filtered out
  entirely, not merely hidden) — asserted in the shell test.
- **"A denied directory appears as unavailable rather than crashing the
  chooser."** `Documents/NoPerm` (mode `000`) is listed with
  `readable:false`, and a direct request to browse into it returns `403`,
  not a crash — asserted in both the shell test and the DOM fixture test
  (denied rows render with a `denied` class and `aria-disabled`, and never
  trigger navigation on Enter/click).
- **"The selection works in supported Safari, Chrome, and Firefox
  versions."** **Not verified.** This repository has no browser-automation
  tool and this environment has none available either (confirmed:
  `chromium`/`google-chrome` are absent). What *was* verified: the extracted
  JS parses (`node --check`) and the dialog's actual logic (root/list
  rendering, focus-trap Tab/Shift+Tab cycling and wraparound, Escape-closes-
  and-restores-focus, arrow/Enter/Backspace navigation, denied-row
  non-activation) passes against a hand-rolled DOM fixture in
  `tests/test_chooser_ui.mjs`, following the same pattern
  `tests/test_jobs_ui.mjs` already established for this repo's
  browser-free JS testing. A real interactive Safari/Chrome/Firefox
  click-through by the owner is the actual gate this criterion asks for and
  has not happened. Recorded as open, not asserted.

## What T1.3 does not include

- Linux/Windows volume ("Drive") discovery — Home only there for now; a
  container target doesn't offer Drive/This-computer scopes at all per the
  T0.1 capability matrix, so this isn't a blocking gap for that target, but
  it is one for a native Linux desktop build (issue #1) once that exists.
- Any wiring into the composer `+` menu or the Chutni Add-Chutni flow —
  neither exists yet; see the scoping note above.
- A real multi-browser interactive verification — see the acceptance-
  criteria note above. This is the one criterion this task cannot fully
  close by itself in this environment.
- A curated "protected directories" denylist beyond dot-prefixed names.
  "Hidden and protected directories are excluded by default" (§5.4) is
  implemented today as: hidden (dot-prefixed) names excluded outright,
  permission-denied names shown as `readable:false`. No additional
  system-path denylist (e.g. hiding `Library`, `System` by name) was added;
  none of this task's acceptance criteria required one, and inventing a
  denylist without a concrete owner-reported nuisance to fix would be
  guessing at a policy rather than implementing one.
