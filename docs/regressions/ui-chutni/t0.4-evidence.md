# T0.4 — Generalize durable background operations: evidence log

Spec: [docs/TASKS_UI_CHUTNI.md](../../TASKS_UI_CHUTNI.md) T0.4 (Phase 0).
Branch: `ui-chutni`. Date: 2026-07-26. Machine: the reference machine (16 GB
Apple Silicon MacBook Air, macOS 26.5.1, Darwin 25.5.0 arm64).

## Approach

T0.4 has no real caller yet: model downloads (T2.2) and Chutni builds
(T4.x) are both unbuilt. Rather than force-migrating the already-tested
Phase-JI job code (`job_state_path`/`save_job_state`/
`append_job_event_file`/etc. in `src/samosa_gateway.c`, exercised
extensively by `tests/test_compiled_gateway.sh`) onto a new abstraction
with no second caller to validate it against, this task adds the
generalized primitive **additively**, as a new header
(`src/durable_job.h`, header-only, matching the project's
`read_cache.h`/`samosa_http.h` convention), included by the gateway and
compiled clean, ready for T2.2/T4.x to call. The existing JI job code is
untouched.

## What landed: `src/durable_job.h`

1. **Path-jailed job directories under an arbitrary root**
   (`durable_id_valid`, `durable_job_dir`). The existing `job_state_path()`
   validates ids the same way but is hardcoded to one gateway-wide
   `g->jobs_root`; `durable_job_dir(base_root, id, ...)` takes the root as a
   parameter, so a model install (`~/.samosa/models/<id>/.partial/<job-id>/`)
   and a Chutni scope build (`~/.samosa/chutni/scopes/<scope-id>/`) can both
   use it without sharing a directory tree.
2. **Atomic state** (`durable_state_put`/`durable_state_get`): the same
   temp+fsync+rename pattern as the existing `write_small_file()`, as a
   reusable pair with an explicit "never silently truncate" read (a
   too-large read returns failure, not partial data).
3. **Durable events matching the frozen §5.7 contract exactly** —
   `{"seq","time","job_id","kind","state","phase","completed","total","unit",
   "current_item","message"}`, with `completed`/`total` as `null` (not a
   fabricated number) when unknown, matching the T0.1 frozen
   `job_event.json` fixture field-for-field. Appends under an `flock` on the
   events file so a concurrent appender can never produce a torn line.
4. **One-writer locks with stale-lock recovery based on verifiable process
   identity, not PID alone** (`durable_scope_lock_acquire`/`_release`,
   `durable_process_identity`, `durable_lock_is_stale`). Real mutual
   exclusion comes from `flock()` (kernel-guaranteed, survives a crash
   automatically); the identity layer is for a caller that wants to
   *diagnose* staleness without blocking (e.g., a future status API
   reporting "the previous build appears to have crashed"). Identity is the
   OS-reported process start time — `sysctl(KERN_PROC, KERN_PROC_PID)` on
   macOS, `/proc/<pid>/stat` field 22 on Linux, degrading to liveness-only
   (documented limitation) elsewhere.

## Two real bugs found and fixed while building this (not merely designed away)

**Bug 1 — `flock()` correctly serializes threads, verified in isolation
first.** Before writing the real test, confirmed with a throwaway probe
that two independent `open()` calls to the same path in one process do
NOT share a lock (`flock` is per open-file-description): first `flock`
succeeds, second `flock(LOCK_NB)` on a separate fd fails as expected. This
gave confidence the primitive's core exclusion mechanism was sound before
building on it.

**Bug 2 — the real one: `durable_scope_lock_acquire` silently defeated its
own lock.** The first implementation called `durable_lock_record()` (which
writes via temp-file-plus-`rename()`) *after* acquiring the `flock`, to
record the acquirer's identity. `rename()` swaps which inode a path points
to; the original `fd`'s `flock` protects the *old* inode, which is now
unlinked from the path. A second `durable_scope_lock_acquire()` call then
opens the *new* (unlocked) inode at that path and its `flock()` succeeds
trivially — the lock was silently bypassable by the exact function meant to
protect it. Caught by the test itself
(`tests/test_durable_job.c`: "second concurrent acquire is rejected while
the first is held" — FAILED on first run). Fixed by writing the identity
record directly into the already-open, already-locked `fd`
(`ftruncate`+`lseek`+`write`+`fsync`), never through a path-based rename
while a lock on that exact path is held. Re-verified: 5/5 clean runs after
the fix.

This is exactly the class of defect T0.4 exists to prevent (a "PID alone"
substitute problem, but one layer deeper — a rename-based state update
silently invalidating the OS-level lock meant to guard it). Recorded here
per the project's evidence-not-assertion rule rather than silently fixed
without a trace.

## Acceptance criteria

The four acceptance criteria in the spec (closing/reopening the browser
reconstructs job state; killing the gateway mid-operation leaves the prior
model/index valid; restart resumes from a checkpoint or reports a
recoverable failure; repeated pause/resume/cancel is idempotent) describe
**end-to-end behavior of a real durable job** — there is no real job yet to
run this against (T2.2/T4.x). What this task can verify now, and did:

- **Crash recovery primitive, directly**: a lock's true holder liveness is
  provably re-derivable after that process exits — `fork()` a child, have
  it record its own (pid, identity), let it exit, confirm
  `durable_lock_is_stale()` correctly reports the lock as stale (not "we
  assume so" — the child process object no longer exists, checked via
  `kill(pid, 0)` returning `ESRCH`).
- **Not fooled by PID reuse**: with our own live pid but a deliberately
  wrong identity value, `durable_lock_is_stale()` reports stale; with the
  correct identity, it reports held. This is the literal "not PID alone"
  requirement, and it is the one a naive `kill(pid,0)`-only check would get
  wrong in exactly the reused-pid case.
- **Idempotent lock lifecycle**: acquire → second acquire rejected →
  release → acquire again succeeds, proving the release path doesn't leak
  the lock and the acquire path doesn't wrongly succeed while held.
- **Events survive replay**: two appended events are both present, complete,
  and exactly two lines (`\n`-delimited) after both appends — no line lost,
  no line torn.

Full end-to-end verification against a real running job (browser
reload/gateway-restart/SIGKILL mid-operation) is deferred to whichever of
T2.2 or T4.5 lands first and actually calls this primitive; recorded here
as the honest state rather than claimed early.

## The interactive-generation interlock is already reusable — verified, not re-wired

Read `interactive_start()`, `interactive_finish()`, `interactive_recent()`,
`interactive_cooldown_ms()` (`src/samosa_gateway.c`) in full: all four
operate purely on `Gateway` atomics (`g->interactive_active`,
`g->last_interactive_mono_ms`) with zero Jobs-specific coupling.
`definition_interlock()` — the function Phase-JI jobs actually call — is a
thin wrapper that additionally emits JI's own SSE `job_paused`/`job_resumed`
events around a call to `interactive_recent()`. A future Chutni
summarization worker (T4.4) can call `interactive_recent(g)` directly and
wrap its own pause/resume around `durable_event_append(..., "paused_chat",
...)` from this task's primitive, exactly mirroring
`definition_interlock()`'s existing pattern but with a durable §5.7 event
instead of an SSE-only one. No gateway code changed here: the interlock
needs no modification to become reusable, it already is. Not writing a
speculative wrapper with no real caller, per the project's
no-premature-abstraction convention.

## Packaging fallout: two hardcoded file lists needed the new header added

Adding `#include "durable_job.h"` to `src/samosa_gateway.c` and rebuilding
surfaced that the release packaging path has **two independent, hardcoded
lists** of which gateway-related files ship, neither derived from the other:

- `tools/package_hf.py`'s `GATEWAY_SOURCE_FILES` (used to build
  `release-manifest.tsv`).
- `dist/install.sh`'s `INSTALL_FILES` addition inside the
  `manifest_field "engine/samosa_gateway.c"` gateway-enabled branch.

`make test` caught this immediately (`tests/test_gateway_installer.sh`'s
staged-compile step failed: `durable_job.h` file not found) — added
`durable_job.h` to both lists alongside the existing `read_cache.h` entry.
Worth flagging for T1.0 (which explicitly touches both of these files):
these two lists drifting independently is itself a latent packaging risk
this task incidentally exposed, not one it fixes.

## What T0.4 does not include

- Any real caller of `durable_job.h` (T2.2, T4.x land those).
- Migrating the existing Phase-JI job code onto this primitive — deliberately
  not done now; the existing code is heavily tested as-is and has no need to
  change until/unless a concrete second caller's requirements justify it.
- A Chutni-summary-specific interlock wrapper — `interactive_recent(g)` is
  already the reusable primitive; a wrapper with no caller would be
  speculative.
