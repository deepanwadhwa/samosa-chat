(common HTTP/auth) and §5.1 (profile/setup). Branch: `ui-chutni`. Date:

macOS 26.5.1, Darwin 25.5.0 arm64).

## What landed (`src/samosa_gateway.c`)

### §5.0 UI-token/Origin session contract (a hard prerequisite for any new
v1 route, built now since T1.2 is the first task to add one)

- **Token generation**: 32 bytes from `/dev/urandom` (chosen over
  `arc4random_buf()` for identical behavior across the project's macOS/Linux
  targets), hex-encoded, written to `~/.samosa/run/ui-token` (dir `0700`,
  file `0600`) on every launch — a restart always generates a fresh token,
  which *is* the rotation the spec asks for; nothing here persists or reuses
  a prior token.
- **Root HTML**: gained `Cache-Control: no-store` (previously absent) and
  substitutes the fixed placeholder `__SAMOSA_UI_TOKEN__` with the real
  token if present. Verified this is a byte-identical no-op against the
  *current* `assets/app.html` (which has no such placeholder yet) — the
  substitution only activates once a future frontend adds the `<meta>` tag.
- **`require_ui_session()`**: validates `X-Samosa-Token` (constant-time
  compare) and, when an `Origin` header is present at all, that it exactly
  matches `http://127.0.0.1:<port>`. A missing Origin is accepted (headless/
  CLI use, per spec) as long as the token is valid.
- `SamosaHttpRequest` gained two more captured headers (`ui_token`,
  `origin`), following the same additive pattern as the `range` field added
  in T0.1.

**Scoping decision, stated plainly**: this task gates only the **new**
routes it adds (`/v1/profile`, `/v1/setup/*`). It does **not** retrofit
token/Origin checks onto the pre-existing Chat/Jobs/`/v1/backends` routes —
doing so would break every existing test that calls them without a token,
and that retrofit is a separate, larger, cross-cutting change the spec
itself frames as eventual ("every `/v1/*` route... This includes profile,
model install/select/remove, filesystem, Chat, Jobs, and Chutni routes" —
a target state, not a same-task requirement). Recorded as a known gap for
whichever task does that migration (plausibly T7.2's security gate, or
folded into T1.3/T2.1 as they add their own new routes).

Also **not built**: the `401 stale_ui_session` reload-once semantics
(distinguishing "never had a valid token" from "had one from a now-rotated
generation"). A single per-process token with no generation history can't
distinguish those cases; a generic `401 invalid_ui_token` covers both today.
Full stale-session UX is a frontend concern (T3.x: detect 401, reload the
page once) once there's a real frontend session to lose.

### §5.1 Profile and setup state

- **`GET/PUT /v1/profile`**: `PUT` validates name is non-empty after
  trimming ASCII whitespace, valid UTF-8, ≤80 Unicode scalar values (not
  bytes — counted via a dedicated `utf8_scalar_count()`, distinct from a
  byte-length check), ≤256 UTF-8 bytes. `GET` before any `PUT` returns
  `404 profile_not_found`, not a crash or an empty-but-200 fabrication.
  Editing an existing name preserves `created_at` and the entire
  `onboarding` sub-object untouched (verified: completing welcome, then
  renaming, does not reset `welcome_completed_at`).
- **`GET /v1/setup/status`**: derives `next_step` in the documented order —
  missing name → `name`; missing `welcome_completed_at` → `welcome`; no
  installed+ready model → `model`; otherwise → `chat`. `POST
  /v1/setup/welcome/complete` is idempotent (verified: two calls one second
  apart return the identical, first-recorded timestamp).
- **Corrupt `profile.json`** (`printf 'not valid json{{{' > profile.json`)
  is handled by `profile_load()`'s existing parse-failure path — which
  already treats "unparseable" identically to "doesn't exist yet" — so
  `GET /v1/setup/status` still returns `200` with `next_step:"name"` rather
  than a `500` or a crash. This wasn't special-cased for corruption; it's
  the natural consequence of treating "no valid profile" as one state
  regardless of *why* it's invalid.
- **Interim bridge, stated explicitly rather than silently assumed**:
  T2.1's model catalog/selection registry doesn't exist yet, so "a
  selected, verified model" (steps 3–5 of the spec's `next_step` derivation)
  has no real state to check. Until then, `next_step` treats a legacy
  `backend_available() && backend_probe()` backend as satisfying "model
  ready," so an existing dogfood install (a real Ornith/Bonsai/Qwen already
  on disk) reaches `chat` instead of being sent to a "choose a model" screen
  it has no real catalog to answer from. T2.1/T2.2 replace this with real
  `selected_model_id`/`active_install_job_id` state — this bridge is
  explicitly temporary and named as such in the source comment.

## Acceptance criteria

- **"Refreshing at every setup step resumes that step."** The state is
  entirely server-side (`profile.json` + backend readiness) and
  `GET /v1/setup/status` is idempotent and side-effect-free, so any client
  that re-queries it on load gets the correct step — verified across
  name → welcome → model in the test.
- **"Losing browser state during a download reconnects through setup
  status or `GET /v1/models/installs`."** No install/download exists yet
  (T2.2); not applicable until then.
- **"Names containing markup render literally and cannot execute script."**
  Verified: `<b>Deepan</b>` round-trips through `PUT`/`GET` as the literal
  string `<b>Deepan</b>` in JSON — `text_json_string()` (used throughout
  this file already) JSON-escapes it, and nothing here ever concatenates
  the name into HTML server-side. (Rendering it safely as text rather than
  `innerHTML` in the browser is T2.4/T3.x's job once a frontend exists to
  render it at all.)
- **"Editing the name updates all welcome text without altering model
  prompts."** No model prompt in this codebase currently interpolates the
  profile name (grepped — none do), so there is nothing to alter; this
  criterion becomes actively checkable once T2.4 builds the welcome copy.
- **"Corrupt profile JSON yields a recoverable setup state and
  diagnostic."** Verified — `200` with `next_step:"name"`, not a crash.
  ("Diagnostic" here is the honest state itself, not a separate log; no
  stderr diagnostic was added for this specific case — a reasonable
  follow-up if T7.x's diagnostics work wants one.)

## What T1.2 does not include

- Token/Origin gating on any pre-existing route (Chat, Jobs, `/v1/backends`)
  — explicit scope decision above.
- `401 stale_ui_session` reload-once semantics — needs a real frontend
  session to have something to "reload."
- Real model selection/install state in `next_step` — T2.1/T2.2's interim
  bridge is named above and will need replacing, not just extending.
- Any frontend screen. This is the server-side contract T1.2 owns; T2.4
  builds the views against it.
